# MF CORE-01 — One Transfer Mutation Owner

**Status:** completed — merge pending  
**Owner:** MoneyFlow  
**Issue/PR:** #152 / #153  
**Last updated:** 2026-07-30

## Outcome

Account and ledger surfaces now use one client-side owner for transfer validation, demo persistence and authenticated mutation execution, while retaining separate UI-state responsibilities.

## Repository reconnaissance

### Previous behavior

- `useTransactions.addTransfer()` validated account identity, constructed demo transfer rows, wrote local storage or called `createTransferAction`.
- `AccountsPage.transfer()` independently performed the same branching and construction.
- The implementations had already drifted: AccountsPage blocked cross-currency transfers before submit, while the ledger hook did not.
- PostgreSQL/RPC remained the authenticated financial authority and already rejected currency mismatch.

### Delivered ownership

| Area | Responsibility after CORE-01 |
|---|---|
| `src/hooks/use-transactions.ts` | ledger state reconciliation only |
| `src/components/accounts-page.tsx` | account balances and notices only |
| `src/hooks/transfer-mutation.ts` | shared client transfer execution |
| `src/lib/transfer-mutation.ts` | pure validation and demo row construction |
| `src/app/actions/transactions.ts` | unchanged authenticated Server Action/RPC |
| `src/lib/transfers.ts` | unchanged pure account-balance application |

### Constraints preserved

- Integer money only.
- Source and destination differ, are active and share currency.
- Transfer remains neutral to total assets and period income/expense.
- Authenticated writes continue through Server Action, viewer validation, RPC and RLS.
- Demo storage is not an authenticated fallback.

## Research

### Question

Should the duplicate implementations be replaced by a generic repository/service layer, full transaction-hook reuse or a transfer-specific executor?

### Evidence

- MF ARCH-01 found a real duplicated authority but rejected forcing AccountsPage to adopt all ledger state.
- Existing MoneyFlow fixes favor the smallest owner extraction that removes a demonstrated failure mode.
- Independent UI reactions remain valid: AccountsPage updates account balances; useTransactions updates the ledger list.

### Decision

Use one bounded transfer executor plus a pure preparation contract. No generic mutation framework, repository class or transaction-domain rewrite was added.

## Specification

### Problem resolved

Two client owners could diverge in validation, error handling, demo construction and authenticated result handling. Cross-currency behavior had already diverged.

## Implementation plan

### Delivered changes

1. Added pure transfer input/account resolution and demo row builder.
2. Added one client executor for demo storage or authenticated Server Action.
3. Replaced both direct create-transfer implementations with executor calls.
4. Added unit and source-contract tests.
5. Kept database/RPC unchanged after all invariants passed.

### Risks and mitigations

| Risk | Mitigation |
|---|---|
| generic abstraction grows beyond one use case | transfer-specific API only |
| account balance applies twice in demo replay | executor reports whether the idempotency-key row is new |
| client validation diverges from RPC | RPC remains final authority; shared client rules cover account/currency constraints |
| storage failure escapes into UI | executor normalizes persistence errors |

## Evaluation

### Findings

- Correctness: cross-currency client drift is removed by one preparation contract.
- Security: authenticated authority remains unchanged.
- Maintainability: two mutation implementations became one without coupling AccountsPage to ledger state.
- UI/UX: no layout or copy redesign; existing success notices remain route-owned.

### Remaining limitations

- Update-transfer still has its own demo construction and is deliberately out of scope.
- Authenticated idempotent replay remains enforced by RPC; UI double-submit protection remains the dialog/form responsibility.
