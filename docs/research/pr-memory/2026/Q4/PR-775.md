# PR #775 — Neon migration PoC: provider seam + scratch-project evidence

- Date: 2026-10-08 (updated after Gates 1–5 and the first review round)
- Change class: PoC/draft (Class 3 boundary — draft PR, no merge request)
- Affected capability or project boundary: adds a feature-flagged backend
  seam (`MF_BACKEND_PROVIDER`, default `supabase`); Neon path is opt-in
  PoC only. No production, provider config, or user-data surface touched.
- Status impact: the migration is technically feasible end-to-end —
  schema, RLS, RPCs, auth (email + Google OAuth initiation), encrypted
  backup/restore, write-freeze, and UUID identity preservation verified
  on the real provider with synthetic data. Review round 1 found and
  fixed a P0 fresh-login bug (data client required before Neon sign-in),
  an npm-10 lockfile gap, and PK-only restore checksums.
- Changed: `db/compat/*`, `db/neon/migrations` (generated, deterministic),
  `scripts/neon-poc/*` (verify-target allowlist, reset, replay, gen,
  coverage test, backup-rehearsal, vertical-slice),

  `src/app/api/auth/[...path]/route.ts`, `src/components/auth-form.tsx`
  (reset token field), `docs/plans/active/neon-migration.md`, package
  deps (`@neondatabase/auth`, `jose`, `embedded-postgres`, `pg`).
- Verified: 80/80 migrations on Neon PG 18 (fresh + repeat); 58/58 pgTAP
  suites local; vertical slice 14/14 through the real app path (register,
  onboarding, dashboard, transaction, accounts, reconciliation,
  stale-`expected_updated_at`, logout, revoked session, A/B isolation,

  backup rehearsal — AES-256-GCM archive → restore into scratch `mf_poc`

  account deletion and step-up re-auth are Supabase-only (fail closed);
  Google OAuth provider-subject binding/collision tests pending;
  real-data export, production egress, merge and cutover stay owner-gated.
- Production/provider evidence: scratch project `moneyflow-neon-poc`
  (`polished-pine-75721729`, PG 18, Free org) with synthetic users only;

- Superseded issue, roadmap or claim: executes #774 (Supabase Free → Neon
