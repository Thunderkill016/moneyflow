# PR #793 — mobile: hybrid Google sign-in (native sheet + loopback redirect)

- Date: 2026-10-14.
- Change class: Class 3 — authentication boundary; a new sign-in path
  replaces the failed native one, touching session creation and the
  delete-account re-auth gate.
- Affected capability or project boundary: `mobile/` auth only — login
  page, delete-account re-auth, Neon auth client. No ledger, schema or
  data-path change; account seeding stays server-side.
- Status impact: implemented and locally verified; not merged, not
  deployed.
- Why: the native `google_sign_in` idToken exchange cannot work against
  Neon Auth's *shared* Google provider — the provider's Google Cloud
  project is owned by Neon and cannot register `app.moneyflow.moneyflow`
  + SHA-1 as an Android OAuth client, so the Credential Manager sheet
  only ever answered `[16] Account reauth failed`.
- Changed: `auth_client` gains `beginGoogleRedirect` (POST
  /sign-in/social with a `localhost:<port>/oauth-callback` callbackURL,
  admitted by upstream `allow_localhost`; captures the planted
  `session_challenge`/`session_challange` cookies) and
  `finishGoogleRedirect` (replays the redirect query incl.
  `neon_auth_session_verifier` to /get-session with the challenge
  cookies as the `Cookie` header; the signed `session_token` cookie
  wins). `data/google_sign_in.dart` becomes the `GoogleSignInFlow` seam
  + `LoopbackGoogleSignIn` — ephemeral `HttpServer` on the loopback
  (IPv6-first, IPv4 fallback), injectable `BrowserLauncher`, `cancel()`
  and a 5-minute redirect bound; only the callback path carrying the
  verifier or an OAuth `error` ends the wait. The login page shows a
  "Đang chờ Google…" dialog whose Hủy aborts the flow; aborts stay
  silent, failures get the honest snackbar. Delete-account Google
  re-auth rides the same flow and now aborts when the browser returns a
  *different* user id — the prior session is restored instead of
  letting the RPC delete the wrong account. A follow-up commit restores
  the native sheet as the preferred leg: `HybridGoogleSignIn` runs
  `NativeGoogleSignIn` only when `MF_GOOGLE_SERVER_CLIENT_ID` is set
  (which only makes sense against an owner-created non-shared Neon
  provider whose Google Cloud project registers the Android client);
  any native failure falls back to the loopback, while a native
  user-cancel propagates silently. `google_sign_in` and the define are
  back, optional.
- Verified: `flutter analyze` clean; full `flutter test` suite green
  (1132) including five transport-level loopback cases driven by a real
  `HttpServer` + `HttpClient` (verifier exchange, cancel-releases-port,
  launch failure, OAuth error redirect, stray-path rejection), five
  hybrid-leg cases (native short-circuit, cancel-is-intent,
  failure-fallback, no-native, cancel fan-out) and the rewritten
  login/delete groups.
- Remaining: physical-device OAuth round-trip on the OPPO CPH2001 and a
  Neon-side `neon_auth.account` provider-row check; the redirect binds
  `localhost`, so the browser must be on the same device (always true
  for a phone).
- Production/provider evidence: none yet — Neon acceptance sandbox is
  configured (`google` shared provider enabled); real sign-in evidence
  follows the device smoke.
- Superseded issue, roadmap or claim: "native Google sign-in requires
  an owner-provided client id" is now a *conditional* gate — with the
  define the native sheet is tried first and falls back to the
  loopback; without it the loopback serves the shared provider with no
  client id at all.
