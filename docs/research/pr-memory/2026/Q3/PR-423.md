# PR #423 — test: derive erasure coverage from the schema instead of a list

- Date: 2026-08-18
- Change class: Class 1 — adds one static test file. No migration, schema, RLS, function, runtime, provider or CI change. The purge function itself is deliberately untouched.
- Affected capability or project boundary: verification of the data-erasure guarantee. Turns "purge covers every tenant table" from a comment into a check that fails when it stops being true.
- Status impact: candidate. Follow-up to a finding recorded in PR #422. Closes no release gate; RRB-04, RRB-05, RRB-06, RRB-09 and RRB-08 all remain open.
- Changed: added `src/lib/tenant-purge-coverage.test.ts`, which derives the tenant table set from the migrations — every table declaring a `user_id` referencing `auth.users` — and requires each to be either deleted by `purge_user_tenant_data` or named in an explicit cascade-only exception list.
- Why: `purge_user_tenant_data` documents itself as purging "every current MoneyFlow tenant row", and `supabase/tests/database/tenant_isolation_and_deletion.test.sql` enumerates expected-empty tables literally. Neither derives its list from the schema, so neither can notice a new tenant table. `archive_restore_batches` and `archive_restore_rows`, added later in `20260812000000_export_user_archive.sql`, are in neither.
- This was never a data leak, and saying so precisely matters: both tables declare `user_id uuid not null references auth.users(id) on delete cascade`, so they are removed when an account is deleted. What drifted is the guarantee's shape — it rests on the cascade rather than on the function claiming to do it, and a flow that purged without deleting the Auth user would leave them behind.
- Anti-vacuity measures, because a guard that cannot fail is decoration: the test reads the **last** definition of the function, since it is redefined across migrations and an earlier more complete version must not satisfy the check; it asserts non-trivial table counts on both sides so a parser matching nothing fails rather than passes; a cascade-only table must actually declare `on delete cascade`, so erasure cannot silently become incomplete if someone drops it; and an exception must still look like a tenant table, so stale entries cannot accumulate.
- Verified: the guard was proven to fail for the real case — removing `archive_restore_batches` from the exception list produces "these tenant tables are neither purged nor declared cascade-only: archive_restore_batches" instead of a green run, and the file was restored afterwards. Local `lint`, `typecheck`, `check:architecture`, `check:knowledge`, `test:ci-policy`, `check:migrations`, 1076 unit tests and `git diff --check` pass. Exact-head provider checks are authoritative.
- Remaining: whether `purge_user_tenant_data` should itself be extended to cover the two archive-restore tables, and whether its comment should be narrowed, are database decisions left to the owner — changing erasure behaviour deserves its own review and a pgTAP run rather than riding along with a test. The hand-maintained pgTAP list is also still hand-maintained; this test guards the purge function, not that suite.
- Production/provider evidence: not applicable. No provider write, deployment, production-data access or production verification. The test reads SQL text and proves nothing about runtime behaviour; the pgTAP suite still owns that.
- Snapshot update: not applicable while Status impact remains candidate. On merge the durable change is a stronger erasure guarantee in verification, not a change to what the product does.
- Superseded issue, roadmap or claim: narrows the accuracy of the `purge_user_tenant_data` comment claiming it covers every tenant row — the claim is now bounded by an explicit exception list rather than left as prose. Supersedes nothing else.
