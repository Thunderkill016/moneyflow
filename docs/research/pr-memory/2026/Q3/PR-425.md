# PR #425 — docs: measure the product against its own four jobs, and archive what drifted

- Date: 2026-08-18
- Change class: Class 0 — documentation only. Sixteen file moves, one new assessment, one archive README, and repointed documentation references. No runtime, test, schema, RLS, Auth, provider, CI or product-surface change.
- Affected capability or project boundary: documentation authority boundary and product direction assessment. No feature is added, removed or altered.
- Status impact: candidate. Closes no gate and changes no release state.
- Changed: added `docs/product/REORIENTATION_2026-08.md` measuring the current product against its own four jobs; moved sixteen superseded documents into `docs/archive/` behind a README that states plainly it is not authority; repointed inbound documentation references.
- What the measurement found: navigation exposes 16 destinations and **seven** serve the four jobs. A quarter serve Inbox, imports and rules, which `AGENTS.md` itself calls "advanced capture tools, not product identity" — so the navigation contradicts the product law printed beside it. Export, one of the four jobs and the one the brand's trust argument rests on, has **no navigation entry at all** and is reachable only inside settings. The full surface is 39 routes, four capture surfaces and two ledger views. Documentation had reached 335 files and 3.8 MB, including five Webflow design-category studies, Framer and UXPilot corpus inventories, and a readiness report from another product's agent framework.
- Two candidates deliberately stayed: `CALM_LEDGER_V2.md` and `SIGNAL_LEDGER_V3.md` are superseded by every documentation argument but are load-bearing for code — `SIGNAL_LEDGER_V3.md` is read directly by three files under `src/` — and a first attempt at moving them broke two tests. Archiving them requires changing those tests, which deserves its own review. The generalisable lesson is recorded in both the archive README and the assessment: inbound **code** references must be checked, not only documentation links.
- Process observation, included because minimalism has to apply to how the project runs: every change pays the same paperwork tax whether it is one line or a subsystem — 130 memory records, 60 completed packets, plus four contract gates. What that machinery bought during the session producing this document is stated rather than assumed: two pull requests rejected for missing their own memory record, a CSS class with no presentation owner, a 44 px target that would have shipped, and a claimed 99 ms performance improvement that was noise. The proposal is therefore not to dismantle it but to let paperwork scale with the risk classes the gates already use.
- Verified: `check:knowledge`, `test:ci-policy`, `lint` and the full unit suite pass after the moves, which is the check that matters here since a naive archive would leave dangling references. Exact-head provider checks are authoritative.
- Remaining: tiers 2 to 4 of the proposal are untouched. Giving export a navigation entry is small and mine to do if authorised; making paperwork scale with risk changes repository policy; and deciding whether Inbox/imports/rules, two ledger views and four capture surfaces earn their place is an owner decision. **No feature is removed on agent judgement**, and usage data would settle those questions faster than argument, which this project does not collect.
- Production/provider evidence: not applicable. No provider write, deployment, production-data access or production verification.
- Snapshot update: not applicable while Status impact remains candidate. On merge the durable change is a documentation authority boundary, not a capability change.
- Superseded issue, roadmap or claim: supersedes nothing. It records that sixteen documents are history rather than authority, which was already true and merely unstated, and it explicitly declines to assert that any product feature should be removed.
