# PR #619 — candidates.propose: agent write capability enters as Inbox candidates (G5)

- Date: 2026-09-20
- Change class: Class 3 (financial/data/security boundary — new write surface, migration, auth claim, transport authorization)
- Affected capability or project boundary: `src/server/capabilities/` (new `candidates.propose`, write gate in `registry.ts`, `write-policy.ts`, per-capability MCP annotations, `clientId` on `CapabilityContext`), `src/server/auth.ts` (`client_id` claim on Viewer), transports (`/api/capabilities/[id]`, `/api/mcp`), `src/lib/inbox/` (agent-proposal id format, review explain line, `agent` source), `src/lib/rate-limit.ts` (write limiter), `supabase/migrations/20260920120000_agent_candidate_proposals.sql`, `docs/agents/capabilities.json` regen, megaplan A4b
- Status impact: implements the v1 slice of the 617 spec; direct-ledger auto-post remains unauthorized/parked
- Changed: `candidates.propose` persists a pending Inbox candidate with `source: "agent"`, never a posted transaction. Idempotency: caller `idempotencyKey` is namespaced into `source_external_id` as `agent|<client|first-party>|<key>` via `src/lib/inbox/agent-proposal.ts` — replays return the existing candidate (`deduplicated: true`), and the approve-time `source_external_id_match` guard plus lifecycle/archive contracts apply unchanged. Write gate in `runCapability`: third-party OAuth clients must be in `CAPABILITY_WRITE_CLIENT_IDS` (fail-closed; Supabase OAuth has no custom scopes); first-party (no `client_id` claim) passes. `capabilityWriteLimiter` 20/60s per viewer+client inside the registry, so all transports share it; REST maps `forbidden`→403 and `rate_limited`→429+`Retry-After`, MCP surfaces `capability_error:<code>`. MCP tool annotations now derive per capability (`readOnlyHint` false for writes). Inbox explain line renders "đề xuất bởi `<client>`" for agent candidates.
- Design revision during implementation: the spec's `oauth_client_id` column was dropped — it would have forced `create or replace` on two hash-pinned archive export/restore functions and archive contract churn. Client identity rides in `source_external_id` instead; same audit value, zero schema surface beyond the enum value.

- Remaining: `test:db` not runnable locally (no Docker) — relies on the CI database lane; `test:e2e` covered by CI browser lane. Merge/deploy remains owner decision.

- Lifecycle impact: adds the first write capability to the registry; megaplan gains A4b marked in-PR; `docs/agents/README.md` and `docs/rate-limit.md` updated for the write path.

## Boundaries

- No direct-ledger/auto-post path; `write:commit` authorization remains unused.
- Agent candidates carry no transaction id and stay `status: pending` until human approval in-app.
- Demo viewers are never authenticated — transports already reject them before the write gate.
- Concurrent same-key proposals can double-insert a candidate row (no unique constraint on `source_external_id`), but the approve-time `source_external_id_match` guard prevents double-posting — same concurrency model as existing import sources.

## Evidence limits

- Local pgTAP (`test:db`) could not run without Docker; the enum-only migration is exercised by the CI database lane.
- RLS isolation for the insert path is inherited (plain `inbox_candidates` insert under the viewer-scoped client, no service role); verified by the existing table policies, not a new live probe.
