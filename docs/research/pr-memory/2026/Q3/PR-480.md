- The defect, verified rather than taken from the issue text: `PRIMARY_NAV` contains a `kind: "action"` capture item, and the sidebar rendered it through `PRIMARY_NAV.map`. The topbar separately renders the capture CTA. Reading `app-shell.module.css` confirms both are visible above 760px — `.primaryAction` is `display: none` only under the 760px breakpoint, and `.primaryNav` stays visible. So a desktop viewport genuinely carried two capture primaries, against the `AGENTS.md` rule of one primary action per viewport.
- Changed: `SIDEBAR_NAV` is `PRIMARY_NAV` without action items, typed `PrimaryNavLink[]` through a type predicate so the compiler enforces the rule rather than a comment; the shell renders it and the now-unreachable action branch is deleted rather than left as dead code. The filter lives in `nav-ia.ts` so the rule is stated once, in the module that owns the information architecture.
- What was deliberately not changed: the capture action stays in `PRIMARY_NAV`, because `mobileTabs` is derived from it and mobile's centred `Ghi` tab is deliberate. A test asserts that explicitly so the sidebar filter cannot later be mistaken for removing capture from the product.
- A test was asserting the violation: `e2e/audit/critical-browser.audit.spec.ts` used `Nhập nhanh` as its **desktop** trigger, so it would have failed on this fix while defending the defect. It now targets the topbar CTA, which is what the product law says the desktop primary is. Recorded because a passing suite that encodes a rule violation is worth naming rather than quietly editing.

Six slices merged since — #468, #470, #472, #474, #476, #478 — made planning the product's differentiating method, so removing its dashboard surface would now work against the direction rather than simplify it. The issue's performance rationale is untouched by this decision, and any future claim there still needs its own measurement; the issue itself already forbids claiming a gain without re-measuring.
