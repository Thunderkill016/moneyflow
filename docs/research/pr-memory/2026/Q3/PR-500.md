# PR #500 — actually watch /api/health

- Date: 2026-08-27
- Change class: Class 1 — one new scheduled workflow and one dependency-free probe script with unit tests. No application code, schema, migration, RPC, RLS, provider or financial-semantic change; nothing in `src/` is touched.
- Affected capability or project boundary: operational monitoring of the deployed health endpoint.
- Status impact: candidate until merged. On merge, the deployment is checked regularly for the first time and a failure notifies the owner without any third-party monitoring account.
- Lifecycle impact: authority transition. No slice is completed or promoted — no current agent-executable slice is registered. What this PR carries is the board's move from PR #499's baseline to PR #499's merged commit `12a4eb37`, which is the transition it is the same-PR projection for.
- Why now rather than in principle: `/api/health` has existed since PR #498 and nothing has called it once. A health check nobody reads is the same as no health check — today, if the site stops serving at 2am, the thing that tells the owner is a user. This is the fourth item on the ordered work list agreed with the owner, and the first one on that list that was not blocked on them.
- Changed: `scripts/probe-health.mjs`, `scripts/probe-health.test.mjs` (9 tests, registered in `test:ci-policy`), and `.github/workflows/health-monitor.yml` running every 15 minutes with `contents: read` and `workflow_dispatch`.
- Two deliberate design choices worth stating. The probe has no dependencies and the workflow does not run `npm ci`, so a broken install can never be the reason the site's health goes unreported. And the judgement lives in a pure `evaluateHealthProbe` function rather than in shell, so the reasons a deployment is called unhealthy are readable and testable without a network.
- The non-obvious check is `cache-control: no-store`. A cached 200 keeps answering "ok" from whenever it was stored, so an outage reads as healthy for as long as that entry lives; the body alone can never establish freshness. A `"dev"` build id is also treated as a failure — not an outage, but a deployment that cannot be traced back to a commit, which makes any problem report from it name nothing.
- Verified: `lint`, `typecheck`, `check:architecture`, `check:knowledge` and `test:ci-policy` (**209 pass**, +9 new) all exit 0. Run against real production rather than asserted: `node scripts/probe-health.mjs` returned `HEALTHY; build: 12a4eb3` with exit 0 — `12a4eb3` being PR #499's merge commit, which also confirms production had already redeployed.
- Proven to fail, not only to pass: pointed at `https://www.moneyflow.app` it returned `UNHEALTHY` with exit 1 and three separate reasons — HTTP 404, a cacheable `cache-control`, and a non-JSON body. Pointed at a non-existent host it also exited 1.
- Remaining: GitHub does not guarantee scheduled punctuality and delays under load are normal, so this is "checked regularly", not "checked to the minute" — **a missed window is not evidence the site was up**. Scheduled workflows are disabled automatically after 60 days without repository activity. The probe proves the deployment still serves requests and nothing more, which is the deliberate shallowness of `/api/health` itself. `workflow_dispatch` could not be exercised because a workflow must exist on the default branch first; what is verified is the exact command the workflow runs. No alert routing beyond GitHub's own workflow-failure notification is configured.
- Production/provider evidence: production was read only — two GET requests to `/api/health` on the deployed build. No write, no deployment, no production-data access.
- Snapshot update: `docs/research/CURRENT_PROJECT_MEMORY.md` and the board both move to the PR #499 baseline `12a4eb37` and carry the PR #500 projection. No capability row changes.
- Superseded issue, roadmap or claim: supersedes the implicit claim in PR #498 that adding a health endpoint delivered monitoring. It delivered the endpoint; nothing observed it until now.
