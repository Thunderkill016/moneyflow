# PR #424 — feat(capture): say what a save adds up to, at the moment of saving

- Date: 2026-08-18
- Change class: Class 2 — bounded user-flow change on two capture surfaces plus one new domain module. No schema, RLS, Auth, provider, CI or financial-semantics change.
- Affected capability or project boundary: the post-save moment on `/capture/quick` and the dashboard. Phase 1.6 of `docs/plans/PRODUCT_DEVELOPMENT_PLAN.md`, and the first change in this project aimed at retention rather than entry cost.
- Status impact: candidate. Touches no release gate; RRB-08 and the P1 items are unaffected.
- Changed: added `src/lib/capture-consequence.ts`, which builds one Vietnamese line from the saved transaction and the running category total for its month; wired it into `capture-quick-page.tsx` and `moneyflow-dashboard.tsx` so a save reads identically on both; removed a `formatMoney` import the dashboard no longer uses.
- Why: five consecutive releases (#404, #408, #410, #412, #414) made recording cheaper and none made it pay off, which is the wrong side of the trade for a manual ledger — people abandon these products because entry buys nothing, not because entry is slow. The evidence was in the code: `/capture/quick`, the surface those releases optimised hardest, returned `"Đã lưu giao dịch."` at the highest-attention moment the app has, while the dashboard returned only an amount, so the two surfaces also disagreed.
- Agreement invariant: the running total is deliberately the same computation `topExpenseCategories` already performs — same month-prefix window, same exact `kind` match preserving transfer neutrality, same treatment of split rows contributing only their own line. A figure here that disagreed with the dashboard would be worse than no figure, and a test asserts the two agree.
- Deliberate silences: transfers get a plain confirmation because they belong to no category total and inventing one would break transfer neutrality; uncategorised rows have nothing to total; and the first entry in a category is the whole total, so repeating it back is noise rather than payoff.
- Product-law boundary, enforced rather than promised: `docs/product/PRINCIPLES.md` forbids presenting spending guidance without a researched contract and reliable income-cycle, commitment and reserve data, and the withheld safe-to-spend figure stays withheld. Restating a user's own recorded numbers is not advice; telling them what to do about those numbers is. A test bans prescriptive vocabulary outright — `nên`, `đừng`, `hãy`, `cảnh báo`, `tiết kiệm`, `cắt giảm`, `hạn chế`, `khuyên` — together with safe-to-spend phrasings, so the boundary is a property of the code.
- Verified: 7 unit tests covering the dashboard-agreement invariant, the split-row case, income never mixing with expense, a previous month not leaking, the three silent cases and the vocabulary ban. Browser proof in `e2e/capture-consequence.spec.ts`: two saves in one category, the second reporting 150.000 while the first stays quiet. The browser helper is preset-aware on purpose, because after the first capture the #412 learned presets make the flow amount-only, and that preset is what keeps both entries in one category. Local `build`, `lint`, `typecheck`, `check:architecture`, `check:css-ownership`, `check:code-css-ownership`, `check:knowledge`, `test:ci-policy`, `check:migrations`, 1080 unit tests and `git diff --check` all pass. Exact-head provider checks are authoritative.
- Remaining: the line currently reports only the category running total. Adding budget context would make it stronger but `capture-quick-page` does not receive `budgets` today, so that needs data threaded through and was left out rather than half-built. Phase 1.7, first-run value before anything is recorded, is untouched and remains the hardest item in the plan.
- Production/provider evidence: not applicable. No provider write, deployment, production-data access or production verification. Physical-device behaviour is not claimed; RRB-08 remains open and owner-owned.
- Snapshot update: not applicable while Status impact remains candidate. On merge the durable change is that recording returns information rather than an acknowledgement, which the capability inventory may be worth reflecting.
- Superseded issue, roadmap or claim: supersedes the plan's description of Phase 1.6 as not started, and retires the two divergent post-save messages in favour of one shared line. Supersedes nothing about #403, #417, #418 or any release gate.
