- The gap: a user could not ask which account the money actually left from. In Vietnam that is an ordinary question, because an ordinary person holds cash plus a bank account plus at least one e-wallet. Accounts are otherwise first-class in this product — multiple accounts, transfers, per-account registers, statement reconciliation — and reports ignored them entirely.
- Changed: `FinancialReport` gains `accounts: { name, amount, share }[]`, filled in one pass over the same expense rows the category breakdown already walks; the reports page renders it beside the category section, reusing the existing category CSS Module classes rather than adding new ones.
- The correctness trap, and it would have been invisible: split rows behave differently for accounts than for categories. The category breakdown distributes a split across its lines because each line names its own category. An account breakdown must **not**, because a split is still one payment leaving one account. Distributing it would under-report every account holding split rows, and the figures would quietly disagree with the account register. The test asserting this also asserts that the same row really is distributed on the category side, so it cannot pass vacuously.
- Transfers are excluded by matching `kind` exactly, consistent with every other aggregate here. That is not incidental: a transfer moves the user's own money between their own accounts, so counting it as money leaving would inflate the funding account while nothing left the user.
