# PR #694 — Standalone backup-file verification on /settings/backup

- Date: 2026-09-23
- Change class: Class 2 (bounded UI/flow addition to one settings surface; no mutation path, no schema, no RPC)
- Affected capability or project boundary: `src/lib/archive/archive-backup.ts` (`verifyArchiveBytes`, `ArchiveVerification(Report)`, `ArchiveCollectionCount`, `describeArchiveCollection`), `src/components/backup-settings-page.tsx` (verify section + terminal `VerifyState`), `src/lib/archive/archive-backup.test.ts` (pure + surface contract tests).
- Status impact: none → implemented. Resilience audit Gap 2: until this PR the only way to learn a backup file was restorable was attempting restore, gated on an empty target account. "Kiểm tra tệp sao lưu" now reports generation (`schema_generation`), `produced_at`, `archive_version` and per-collection row counts for all 19 contract collections entirely on-device.
- Changed: `verifyArchiveBytes` composes the existing outermost ingress (`payee-archive-ingress.ingestArchiveBytes` — byte bound, strict UTF-8, duplicate-member scan, JSON syntax, R5 contract) with `summarizeArchive`; no validation logic is re-implemented. The page reuses the `dateField` file input + `role=status` + `resultGrid`/`resultRow` patterns; the demo banner copy was updated because verify genuinely works in demo (pure local inspection, zero writes, zero network).
- Design decisions: (1) the verify result type deliberately carries no eligibility field — `valid` means structurally valid, and the card states plainly that only a real restore proves restorability ("tệp hợp lệ" ≠ "có thể khôi phục"); (2) verify is not gated on `ARCHIVE_MAX_RESTORE_BYTES` (4 MiB transport cap bounds uploads only) — files up to the 64 MiB ingress bound verify, and when `bytes > ARCHIVE_MAX_RESTORE_BYTES` the card adds a line saying the file is too large to restore via this page; (3) `VerifyState` is terminal (`idle → checking → valid | invalid`) with no `confirming`/`restoring` kinds to reach; (4) `ArchiveSummary` and the restore dialog were left untouched.
- Verified: `npm run typecheck` clean, `npm run lint` 0 errors (1 pre-existing warning in `quick-add-defaults.test.ts`, untouched), `npm run test` 1757/1757, `npm run build` green, `check:knowledge` pass, `test:ci-policy` 191/191, `check:css-ownership` pass, `check:architecture` pass. New tests pin: envelope + per-collection report, ingress-rejection passthrough, tampered-count fail-closed, no restore-eligibility field, Vietnamese label completeness, and a surface contract test that verify cannot reach `restoreArchiveAction`/`setRestore`/confirming-restoring kinds.
- Remaining: `test:db`, e2e and visual audit not runnable locally — the WCAG audit route list already includes `/settings/backup`, so CI's browser lanes carry that evidence. UI-only until a user picks a file; verify a real downloaded backup post-deploy.
- Production/provider evidence: none at open; no provider or data writes exist in this change.
- Superseded issue, roadmap or claim: resilience audit Gap 2 (verify-before-restore affordance).
- Lifecycle impact: if the archive contract gains collections, `ALL_ARCHIVE_COLLECTIONS` drives the report automatically but `describeArchiveCollection` needs a label per new collection — the label test fails closed on a missing one (raw-key fallback is the tell). If a future "restore eligibility preview" is requested, it must not grow out of `VerifyState`/`ArchiveVerificationReport` — honest eligibility requires the server, not file inspection.
