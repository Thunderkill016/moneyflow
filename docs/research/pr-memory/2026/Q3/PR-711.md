# PR #711 — Frequent Patterns: recurring exclusion + benchmark P-cohort

- Date: 2026-09-24
- Change class: Class 2 (domain logic + `public/` browser asset; no schema,
  no migration — CI selects browser smoke + responsive audit lanes for the
  public HTML tool)
- Affected capability or project boundary: `src/lib/quick-add-defaults.ts`
  (pattern/preset derivation consumed by `add-transaction-dialog.tsx` on
  `/capture/quick`), `public/capture-bench.html` (offline measurement tool),
  Capture V2 packets.
- Status impact: Capture V2 Slice 1 stays a reversible prototype. Recurring-
  owned rows can no longer train capture presets/patterns; the benchmark can
  now measure pattern-assisted capture against the #596 control by cohort.
- Changed:
  - `deriveStableLedgerPreset` and `deriveFrequentLedgerPatterns` filter
    `isRecurringPayment` — recurring-generated rows are rule output owned by
    the recurring/commitment domain, not manual-capture evidence.
  - `derivePayeeCategorySuggestion` intentionally unchanged: a recurring
    rule's category remains user-chosen evidence for where that payee
    belongs, offered only as an explicit suggestion chip.
  - `capture-bench.html`: tasks P1–P3 (`group: "pattern"`), tagged
    `bench-seed-*` demo seeding (5 reviewed rows → exactly 2 chips), unseed
    restoring the demo baseline, `fu-pattern` chip-usage followup, `pattern:`
    column in the report, median aggregation for the pattern group.
  - `matchExpect` verifies `accountId`/`categoryId` when a task declares
    them — wrong-chip captures read `khác-kỳ-vọng` instead of passing on
    kind+amount alone (technical-director review finding).
  - Seed ids excluded from `findNew` so seed writes can never be timed as
    ledger saves; unseed removes only `bench-seed-*` rows and drops the key
    when nothing else remains.
  - Packets updated: recurring exclusion added to the Frequent Patterns
    safety list (with the payee-evidence boundary); benchmark packet
    documents the seed exception, P-cohort tasks and honest limits.
- Verified: unit suite 1848/1848 (quick-add-defaults 22/22 incl. 3 new
  regression pins, bench contract 5/5), `npm run typecheck`, lint clean (1
  pre-existing warning), production build, `check:knowledge`,
  `test:ci-policy` 191, `check:architecture`, `check:css-ownership`.
  Browser smoke on demo (dev :3100): seed → 2 chips → amount preserved on
  tap → save lands pattern context with `reviewed` status → unseed → chips
  absent at support <2.
- Review hardening: technical director (codex exec channel) read the diff
  and caught that `matchExpect` verified only kind/amount — P2's
  "choose the right chip" could pass while picking the wrong pattern;
  fixed with optional context expectations before the PR.
- Remaining: prototype not yet promoted — needs real benchmark runs
  (stable-history vs first-time vs multi-pattern cohorts) before
  keep/change/kill; optional counterparty in pattern identity deferred to
  Slice 3; payee stays out of pattern keys in this slice.
- Production/provider evidence: none — not deployed, no schema.
- Superseded issue, roadmap or claim: implements the eligibility intent of
  `capture-v2-low-maintenance-acquisition.md` Slice 1 and the cohort
  requirements of `capture-v2-benchmark-harness.md`; "recurring stays
  domain-owned" is now enforced in code, not only in prose.
- Lifecycle impact: if a future slice reuses `eligibleReviewedTransactions`
  for new capture-learning features, the recurring exclusion must be
  evaluated per consumer — it is applied at the preset/pattern call sites,
  not inside the shared helper, precisely so payee evidence stays usable.
