# PR #682 — Optimistic delete + update in useTransactions

- Date: 2026-09-23
- Change class: Class 1 (bounded code in one subsystem — the transaction hook and its optimistic reducer — with straightforward branch-revert rollback)
- Affected capability or project boundary: `src/lib/optimistic-transactions.ts` (`reduceOptimisticTransactions` becomes a discriminated mutation union — `add` keeps pendingKey retirement, `remove` filters by id, `update` swaps in a draft; new shared `buildUpdatedTransaction`), `src/hooks/use-transactions.ts` (`deleteTransaction` and `updateTransaction` dispatch the mutation inside `startTransition` before awaiting the server action; demo keeps the synchronous `commitDemoTransactions` path via the same builder), `src/lib/optimistic-transactions.test.ts` (+14 tests), `src/lib/p3-remediation.test.ts` and `src/lib/performance-observability.test.ts` (call-site/regex updates for the union signature).
- Status impact: single-row delete and edit previously awaited the RPC before mutating local state — a confirmed delete left the row visible until `soft_delete_money_transaction` returned. Both now render instantly through the same `useOptimistic` layer create already used, with structural rollback on failure.
- Changed: `remove` hides the row the moment the `SecondaryReviewDialog` confirm resolves; on failure the transition settles with no base write and the stored row returns untouched. `update` shows a draft merged by `buildUpdatedTransaction` (the same merge demo mode commits), skipped only for recurring rows the server would reject with `recurring_payment_locked`. No pendingKey retirement is needed for delete — `transaction_feed` excludes `deleted_at`, so a refreshed feed cannot resurrect the row and the op replays harmlessly over any base. Undo is unchanged: the pre-delete snapshot re-inserts via `restoreTransactionInList` after the delete transition settles. Bulk review/category/date/delete stay confirm-first and sequential.
- Verified: typecheck, lint (1 pre-existing warning in unrelated `quick-add-defaults.test.ts`), 1664/1664 unit tests, check:knowledge, test:ci-policy (191/191), check:architecture, check:capabilities. Local `node_modules` replaced with a hardlinked copy per worktree convention. Browser smoke delegated to CI lanes — the repo's node test harness has no React renderer, so hook behaviour is evidenced by reducer replay-semantics tests plus source-contract assertions.
- Remaining: a replayed `update` op lands on the early-arriving confirmed row for the remainder of its transition (same id, same edited fields — mirrors the create "Đang lưu…" convention); a sub-frame window between `deleteTransaction` resolving and the overlay drop exists before undo is reachable, unreachable in practice because `Hoàn tác` only appears after the promise resolves. Deleting a `pending:*` optimistic row still fails id validation server-side and rolls back — pre-existing behaviour.
- Production/provider evidence: none (no migration; production verification remains an owner decision post-merge).
- Superseded issue, roadmap or claim: none.
- Lifecycle impact: if a future mutation class (e.g. per-row review toggle) wants the same treatment, the union extends by one variant; if the feed ever surfaces `deleted_at` rows, the `remove` op must gain explicit filtering parity rather than relying on view exclusion.
