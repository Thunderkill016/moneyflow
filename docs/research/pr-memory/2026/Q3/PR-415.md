- Measured result — **no performance improvement is demonstrated.** Same methodology, before = CI `31965310083` at `84c9bf8` (its `src/` tree is byte-identical to `main@8ef322ba`), after = CI `31989167370` at head `6832b07`. `/`: LCP 2804 → 3275 ms, score 95 → 92, script transfer identical at 195,787 B. `/dashboard`: LCP 3956 → 3857 ms, TBT 113.0 → 150.5 ms, script transfer 311,601 → 311,603 B. `/` has no runtime change in this branch, so its +471 ms LCP swing is the harness's single-run noise floor and it dwarfs the −99 ms seen on `/dashboard`. LCP misses the 2.5 s budget on both routes; CLS (0) and TBT (≤ 200 ms) pass. The harness now samples each route three times and reports a median with the observed spread. Running that median harness on head `6832b07` on a second machine measured the noise floor directly: LCP range 469 ms on `/` and 684 ms on `/dashboard` across three samples of one build, against a perfectly stable script-byte range of 0 B. That independently confirms the byte figures are trustworthy while single-run timing figures are not, and that the −99 ms once read as a dashboard gain is inside variance.
- Remaining: #403 acceptance 3 is **not met** — there is no material measured improvement, only a named bottleneck. The measured bottleneck is main-thread/hydration cost after first paint (server response 5–15 ms; FCP ~1.69 s against LCP 3.3–3.9 s; `/dashboard` JS bootup 766 → 814 ms against 311.6 KB transferred script), so an LCP win requires reducing the dashboard client component tree, which this branch deliberately does not attempt. The `loading.tsx` boundary serves acceptance 4 (perceptible client-side navigation response) and shows no cold-load Lighthouse gain, which is not claimed as one.
