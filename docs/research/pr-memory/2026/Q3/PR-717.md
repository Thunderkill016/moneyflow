# PR #717 — Budget threshold: "over" decided on raw đồng, not rounded percent

- Date: 2026-09-25
- Change class: Class 1 (bounded code change — one domain module plus its
  tests; CI selects verify + browser smoke, codeql; database false,
  ui-audit false per doctor). No schema, no migration, no server action.
- Affected capability or project boundary: `src/lib/planning/budgets.ts`
  `budgetThreshold`/`budgetStatusLabel` — the shared near/over derivation
  behind dashboard attention chips (`src/lib/attention.ts`), the featured
  budget card and `/budgets` status/bars.
- Status impact: closes issue #714 (surfaced in PR #713 director review).
  Budget copy no longer claims an overshoot that integer đồng do not show.
- Changed:
  - `budgetThreshold` returned "over" whenever the *rounded* percent hit
    100, so 4.990.000 ₫ / 5.000.000 ₫ (99.8% → 100) rendered
    "Đã vượt 10.000 ₫" while 10.000 ₫ remained. "over" now requires
    `spent > limit` on raw integer đồng; the rounded percent keeps driving
    only the watch/near bands and displayed %.
  - Boundary decision — `spent == limit` is **near, not over**: at zero
    overshoot "Đã vượt X" would print "Đã vượt 0 ₫", the same class of
    false claim as the defect. This is the issue's preferred option and
    matches `budgetEffectiveThreshold`'s existing `available < 0`
    (strict `>`) convention. The old pin
    `1.000.000/1.000.000 → "over"` encoded the rounded behaviour and was
    updated to `"near"` with a comment.
  - Degenerate limits: `spent > limit` also makes non-positive caps
    truthful (e.g. limit 0, spent 5.000 → "Đã vượt 5.000" instead of a
    progress-0 "ok"); `limit <= 0 && spent <= 0` still resolves to "ok"
    via `budgetProgress` returning 0.
