# PR #677 — Bulk date edit + soft delete with per-row skip reasons

- Date: 2026-09-22
- Change class: Class 2 (bounded UI/flow — two new actions inside the existing ledger bulk bar)
- Affected capability or project boundary: `src/lib/transaction-review.ts` (plan/apply/skip-summary domain: `planBulkDateChange`, `planBulkDelete`, `applyBulkDateChange`, `summarizeBulkSkips`, `bulkSkipReasonForFailure`, `bulkOccurredOnLabel`, shared `BULK_SELECTION_LIMIT`), `src/hooks/use-transactions.ts` (`bulkUpdateDate`, `bulkDeleteTransactions` — sequential per-row RPC loops with per-item skip reporting, demo path through the local store), `src/app/actions/transactions.ts` (`TransactionActionResult` failure gains a stable `code`; `transaction_reconciled` now maps to real copy), `src/components/transactions/transactions-workspace.tsx` (bulk `Đổi ngày` + destructive `Xóa đã chọn`, two `SecondaryReviewDialog`s, array-based `pendingUndo`), `transactions-workspace.module.css` (`.bulkEditActions` joins the shared flex/stacking rules).
- Status impact: bulk selection previously only offered review-status and category changes; date edit and soft delete now exist without any new ledger-write path — every row goes through the same `update_money_transaction` / `update_account_transfer` / `soft_delete_money_transaction` RPCs the single-row actions use, so RLS, `recurring_payment_locked` and the `transaction_reconciled` trigger apply unchanged.
- Changed: bulk plans partition the selection into eligible rows and skipped rows with grouped Vietnamese reasons (recurring, split lines, no-op date, missing destination, stale/optimistic ids); skipped rows keep their selection so the notice's reasons map to the rows still waiting. Bulk delete keeps the 8-second `Hoàn tác` window by holding snapshots as an array and restoring each via the existing restore RPC. Reconciled rows are only detectable server-side — they surface post-run via the new `code` field.
- Verified: typecheck, lint (1 pre-existing warning), 1535/1535 unit tests, build (51 routes), check:knowledge, test:ci-policy (191/191), check:architecture, check:css-ownership, check:code-css-ownership, check:dead-css, check:migrations, check:deployment-env. Browser smoke and cross-device audit delegated to CI lanes.
- Remaining: sequential per-row actions mean a mid-batch network drop leaves a partial batch — reported per row and retryable; no measured need for a single-roundtrip bulk RPC at the ≤100 selection cap. Demo-mode fixtures carry no recurring/split rows, so those skips are only exercised by unit tests and authenticated data.
- Production/provider evidence: none (no migration; production verification remains an owner decision post-merge).
- Superseded issue, roadmap or claim: none.
- Lifecycle impact: if bulk edits grow beyond the 100-row cap or users need bulk amount/account edits, revisit whether a dedicated bulk RPC is worth the new ledger-write surface; the per-row contract already carries the codes needed to extend skip reasons.
