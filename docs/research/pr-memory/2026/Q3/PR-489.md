# PR #489 — feat(shell): tell the truth about connectivity

- Date: 2026-08-27
- Change class: Class 2 — bounded shell/flow change plus one new deterministic domain module and one client hook. No schema, migration, RPC, RLS, provider or dependency change; no ledger mutation and no change to what a save does.
- Affected capability or project boundary: the shared app shell, the quick-capture dialog's failure message, and a new `src/lib/connectivity.ts`.
- Status impact: candidate until merged. It adds connectivity awareness. It does **not** add offline capability, and the record says so because the difference is easy to overstate later.
- Lifecycle impact: completes current slice. Issue #488 is registered and delivered in this same PR, which carries its own post-merge convergence: the board projection names PR #489, no successor slice is promoted, and projected current memory is updated here. `plan:resolve` intentionally reports NOT READY while this is unmerged.
- Why this was the last audit gap worth taking: `navigator.onLine` appeared nowhere in `src/`, and `public/sw.js` handles push notifications only — no `fetch` handler, no cache, no offline document. For a product whose core job is recording a payment at the moment it happens, in a basement car park or a market with weak signal, the app discovering the problem only after the user commits an action is the wrong shape.
- What was **not** wrong, checked before building: nothing was being lost. `add-transaction-dialog.tsx` sets an error and returns on a failed save without clearing the form, so typed input survives. The defect was narrower than it first appeared — the app did not know, and then gave advice that could not work: `"Mất kết nối khi lưu. Hãy thử lại."` recommends the one action guaranteed to fail until connectivity returns.
- Changed: `connectivity.ts` exporting `readConnectionState`, `connectionNotice` and `saveFailureMessage`; `useConnectionState` subscribing to `online`/`offline`; a quiet persistent notice in the shell beside the demo banner; the capture dialog's failure message routed through `saveFailureMessage`.
- The asymmetry this module exists around, encoded rather than assumed: `navigator.onLine === false` is trustworthy and `true` is not, because a browser reports online whenever it holds any network interface — a captive portal, a router with no upstream, one bar carrying nothing. The states are therefore `offline` and `assumed-online`, never `online`, and a test asserts the name itself so a later reader cannot treat `true` as proof a request will succeed.
- Hydration: the hook starts at `assumed-online` and reads the real value in an effect. Server rendering has no `navigator`, so reading during render would give the client a different first paint and mismatch hydration; `readConnectionState(undefined)` returning `assumed-online` is tested for that reason.
- Presentation judgement recorded because it is a choice, not a default: the notice uses muted surface and text tokens rather than attention colours, and is not a dialog. Losing signal is not something the reader caused and not something they can act on, so interrupting them mid-entry would be a worse answer than letting them keep typing. A browser test asserts no dialog appears and navigation stays usable.
- The boundary, stated so it cannot be read past: **nothing is queued, cached or retried.** No service-worker `fetch` handler, no write queue, no sync. A user still cannot record anything while disconnected. A real offline ledger needs conflict resolution and a sync model and is a separate researched specification. A test asserts the module contains no `setTimeout`, `fetch(`, `localStorage` or queue, so a sync path cannot appear in it quietly.
- Verified: `typecheck`, `lint` (0 errors), `test` (**1198 pass**, +7 unit), `check:architecture`, `check:css-ownership`, `check:code-css-ownership` (after a real build, as that gate requires), `check:knowledge`, `test:ci-policy`, `check:migrations`, and `npm run build` with `NEXT_PUBLIC_APP_MODE=authenticated`. Two new browser specs were run locally against Chromium and a screenshot reviewed: the notice appears on `offline`, the balance stays readable beneath it, it clears on `online`, no dialog traps the page.
- My browser evidence was weaker than I claimed, and CI caught it. The first version asserted a named sidebar link stayed usable. That passes on desktop and cannot pass on a phone, where the sidebar is hidden and the bottom tab bar carries the links — I had run only `--project=chromium` locally and described the result as browser evidence. The assertion is now viewport-agnostic, naming no nav item, and both specs were re-run against `chromium` **and** `mobile-chromium` before pushing.
- Limitation, not a pass: `test:db` was not run — `agent:doctor` reports `missing required capabilities: depends on docker`. The full `test:ui-audit:pr` was not run locally, so the notice's behaviour at 320px and in dark theme is asserted from tokens rather than measured. Provider checks on the exact PR head are authoritative. The browser proof used `context.setOffline` plus a dispatched event, which exercises the listener path but is not the same as a real radio losing signal.
- Remaining: the `online` event fires when an interface returns, not when the internet does, so the notice can clear while requests still fail — the same asymmetry, in the other direction, and not something this slice can fix without probing the network. Only the quick-capture dialog routes its failure message through `saveFailureMessage`; the other mutation surfaces still say "Mất kết nối khi …" on their own. Offline capability remains unbuilt and unpromised.
