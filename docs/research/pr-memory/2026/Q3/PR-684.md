# PR #684 — Recent-payee quick-pick chips + canonical-spelling offer

- Date: 2026-09-23
- Change class: Class 2 (bounded capture-dialog UI + two pure domain helpers; no migration, schema or RPC change)
- Affected capability or project boundary: `src/lib/quick-add-defaults.ts` (new pure `deriveRecentPayees`, `deriveCanonicalPayeeOffer`), `src/components/add-transaction-dialog.tsx` (chip row inside the optional-details disclosure), `src/components/transactions/capture-fast-path.module.css` (`.payeeChipRow`, `.categoryChip[aria-pressed]`, forced-colors outline), tests in `src/lib/quick-add-defaults.test.ts` and `src/lib/ghi-chi-dialog-contract.test.ts`.
- Status impact: the payee `<datalist>` is unreliable on iOS Safari (tap-to-fill bugs) and every new spelling variant fragments "Chi theo nơi", which groups by exact trimmed spelling. Recent-payee chips offer up to four of the user's own most-recent spellings; the canonical offer shows "Dùng 'Grab'?" when the typed value `normalizeSearchText`-equals exactly one distinct stored spelling but is not byte-equal.
- Changed: `deriveRecentPayees(transactions, limit)` orders distinct trimmed non-empty payees by canonical ledger recency (`compareLedgerRecency`) — same trust contract as `derivePayeeSuggestions` (user's own strings, verbatim offers, no normalization) but recency-ordered and caller-capped (dialog passes 4). `deriveCanonicalPayeeOffer(transactions, payee)` returns the single stored spelling that fold-equals the trimmed typed value without byte-equaling it; zero or multiple candidates return null. Both render through `applyPayeeChange`, so a chip tap also re-evaluates saved deterministic rules (#681) and the contract-pinned `setPayee(value)` write set is unchanged. The offer chip hides while the field value matches a recent-payee chip (`!recentPayees.some(...)`), preventing a yo-yo offer right after a tap. Chips reuse `categoryChip` styling inside a new wrapping `payeeChipRow`; `aria-pressed` marks the chip whose spelling the field already holds.
- Verified: typecheck clean, lint 0 errors (1 pre-existing warning in quick-add-defaults.test.ts), `npm test` 1663/1663 (new: 5 deriver tests + 1 dialog-contract test), check:knowledge, test:ci-policy 191/191, check:css-ownership. Browser smoke and visual audit delegated to CI lanes.
- Remaining: chips and the offer are derive-only over the in-memory `transactions` prop — hosts that pass a partial ledger window produce a partial recency view. Physical iOS Safari tap behavior not device-verified locally.
- Production/provider evidence: none (draft-only UI; production verification remains an owner decision post-merge).
- Superseded issue, roadmap or claim: none.
- Lifecycle impact: if the edit dialog later gains a transactions-backed recency source, the same derivers apply — it was intentionally untouched here because it lacks `applyPayeeChange`/rule fill and takes `payeeSuggestions` as a prop. If canonical offers should prefer the most-frequent or most-recent spelling among several candidates, extend `deriveCanonicalPayeeOffer` rather than adding a second spelling path.
