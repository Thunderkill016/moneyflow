# PR #504 — stop allowing every HTTPS host as an image source

- Date: 2026-08-27
- Change class: Class 2 — one production security header tightened, with tests. No schema, migration, RPC, RLS, provider or financial-semantic change; no ledger value or calculation touched.
- Affected capability or project boundary: the Content-Security-Policy served on every response.
- Status impact: candidate until merged. On merge the policy stops permitting arbitrary third-party image sources, and the one deliberate relaxation left in it carries its reason in the code.
- Lifecycle impact: authority transition. No slice is completed or promoted — none is registered. It carries the board's move to PR #503's merged commit `4dcdef4e`, the transition this PR is the same-PR projection for.
- The question asked was whether `'unsafe-inline'` could be removed, and the answer is no, for a measured reason rather than a vague one. Next's own bundled documentation states you "must use dynamic rendering to add nonces". This app prerenders **35 of its 51 routes** as static content — counted from the build output — so a nonce turns every one of them into a per-request function invocation, and production currently measures LCP 2.4 s and CLS 0 on throttled mobile. Hashes do not work either: Next's inline scripts carry per-page flight data (`self.__next_f.push(...)`), so they differ per page and per build and cannot be enumerated ahead of time.
- What was tightened instead is real. `img-src` allowed the bare scheme `https:`, which makes **any HTTPS host on the internet** a legal image source — a tracking-pixel and exfiltration channel bought for nothing. Measured on production across `/`, `/login`, `/security` and `/privacy`: 3 images and 12 fonts, all from the app's own origin, zero third-party. `avatar_url` exists only in the archive schema and is never rendered. `data:` and `blob:` remain because an uploaded receipt is previewed locally before it is sent anywhere.
- Changed: `src/lib/security-headers.ts` — `img-src` narrowed to `'self' data: blob:`, and the `'unsafe-inline'` decision documented at the line that makes it, with the route count, the measured performance at stake, and the reason hashes are unavailable; `src/lib/security-headers.test.ts` gains two tests; `CHANGELOG.md` records both under an unreleased Security heading.
- The new guard is deliberately wider than the line it fixes: no fetch directive — `default-src`, `script-src`, `style-src`, `img-src`, `font-src`, `connect-src`, `media-src`, `worker-src`, `manifest-src`, `frame-src` — may carry a bare scheme (`https:`, `http:`, `ws:`, `wss:`, `ftp:`), checked in both captcha configurations. A bare scheme is the absence of a policy wearing the shape of one.
- What still limits the damage from `'unsafe-inline'`, and why it is defensible: `script-src-attr 'none'` blocks inline event handlers such as `onclick=`, `object-src 'none'` and `base-uri 'self'` close the two classic bypasses, and every other directive is now an allowlist with no wildcard. The comment says to revisit this if the app ever becomes predominantly dynamic, because the trade reverses then.
- Verified: `lint`, `typecheck`, `check:architecture`, `test:ci-policy`, `check:knowledge`, `check:release-version` exit 0; `npm test` **1226 pass, 0 fail** (+2); `npm run build` exit 0. Proven in a browser against the production build rather than by reading the header: 12 routes including the landing page (`next/image`) and `/login` (Turnstile) reported **0 CSP violations and 0 broken images**.
- One measurement I nearly got wrong and corrected: the first browser pass reported a dozen "Refused to execute script" lines. They are not CSP violations — they are `/_vercel/insights/script.js` and `/_vercel/speed-insights/script.js`, which exist only when deployed on Vercel and return the 404 HTML page locally, so the browser rejects them on MIME type. The filter was narrowed rather than the count accepted.
- Proven to fail, not only to pass: restoring `https:` to `img-src` turned the suite red with `img-src must not allow the bare scheme https:`. It was then restored.
- Remaining: `'unsafe-inline'` stays in `script-src`, and `style-src` keeps it too — that one was not investigated here and is a separate question. No CSP reporting endpoint exists, so there is no way to learn what a stricter policy would break other than by shipping it. `connect-src` allows `https://*.supabase.co` rather than the project's own subdomain, which is wider than necessary and was left alone because narrowing it needs the deployment's project ref and would break preview environments configured against a different project.
- Production/provider evidence: production was read only — page loads across four routes to measure which hosts actually serve images and fonts. No provider write, no deployment, no production-data access.
- Snapshot update: `docs/research/CURRENT_PROJECT_MEMORY.md` and the board move to PR #503's baseline `4dcdef4e` and carry the PR #504 projection. No capability row changes.
- Superseded issue, roadmap or claim: supersedes the open question of whether `'unsafe-inline'` can be removed from `script-src`; it cannot without converting the app to dynamic rendering, and that answer is now recorded in the code rather than rediscovered.
