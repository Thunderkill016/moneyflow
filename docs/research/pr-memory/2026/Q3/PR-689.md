# PR #689 — Next-occurrence line on commitment cards + expected-income suffix on the dashboard remainder

- Date: 2026-09-22
- Change class: Class 2 (bounded UI — one disclosure suffix on the statement remainder and one context line on commitment cards over tested pure helpers; no migration, schema, RPC or provider change)
- Affected capability or project boundary: `src/app/dashboard/page.tsx`, `src/components/moneyflow-dashboard.tsx` (incomeTemplates prop + demo hydration), `src/lib/planning/commitments.ts` (`nextOccurrence`), `src/components/planning/commitments-page.tsx` (card line), `src/lib/insights-goals-card.test.ts` (THU-41/#426 contract narrowed), `src/lib/dashboard-phase4-contract.test.ts`, `src/lib/planning/commitments.test.ts`, `src/lib/planning/committed-remainder.test.ts`.
- Status impact: candidate → implemented. The dashboard remainder now discloses declared expected income (`· chưa gồm X ₫ thu dự kiến`) instead of ignoring it, and each commitment card names its next declared occurrence (`Kỳ tới: dd/mm`). Both still withhold on incomplete or malformed inputs.
- Changed: `page.tsx` passes `incomeTemplates` from `getDashboardPageWorkspace` into `MoneyFlowDashboard`; the client hydrates demo templates from `readStoredIncomeTemplates() ?? props` with `dueDate` re-derived for the month and `hydrateIncomeTemplatesWithOccurrences` for received flags — the same precedence `/income-templates` uses — then feeds `buildCommittedRemainder`. Income is disclosed, never folded into the figure. New pure `nextOccurrence(commitment, today, paidThroughMonth)` returns this month's `dueDate` when unpaid-and-ahead (incl. today), next month's clamped `dueDay` when paid or past, and `null` for archived rows, malformed dates/dueDays, a `dueDate` outside the resolved month, or fields resolved for a different month than today's. Cards render it as a `planningStyles.context` line between metrics and actions.
- Verified: `npm run typecheck` clean, `npm run lint` 0 errors (1 pre-existing warning, untouched), `npm test` 1716/1716 (8 new cases: 6 `nextOccurrence`, 1 omitted-templates suffix absence, contract pins), `npm run build` 52 routes, `check:knowledge`, `test:ci-policy` 191/191, `check:css-ownership`. Browser smoke/visual audit delegated to CI lanes.
- Remaining: THU-41/#426 narrowed by explicit scope decision — income-template rows may hydrate the dashboard client boundary as remainder *inputs*, while planning *surfaces* (DashboardPlanningColumn, SavingsGoal, PlanningCard, income page UI) stay excluded; owner may revert the prop wiring without losing the helper. Demo remainder still withholds while the USD fixture account exists (refusal path is the demo-visible behavior). No local browser render evidence.
- Production/provider evidence: none (read-only derivation, no migration; production verification remains an owner decision post-merge).
- Superseded issue, roadmap or claim: PR-679's "remainder excludes expected income on the dashboard by deliberate boundary choice" remainder note — superseded; the boundary now admits income rows as data inputs only.
- Lifecycle impact: if a second dashboard consumer needs income rows, revisit whether the contract narrowing stays bounded; `nextOccurrence` is per-month resolved data only — any multi-month horizon needs a new spec, not a loop over this helper.
