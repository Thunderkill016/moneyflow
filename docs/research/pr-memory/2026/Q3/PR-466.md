- The defect: `parsePasteLine` selected `amounts[0]`, the leftmost extracted token. Every Vietnamese bank SMS opens with the account number, so the account number was systematically read as the transaction amount. Measured on `main@39750077` against eight real bank formats: **2/8 amounts correct**. Only MoMo (message contains no account number) and TPBank (account masked as `0339 xxxx 12`) parsed correctly. Passing `sourceHint: "sms"` changed nothing.
- Why filtering could not fix it: a bare account number clears every guard already present in `extractAmounts` — over 1000, outside the 1900–2100 year window, unprefixed by `[*#xX]`, and long enough to skip the `looksGrouped` requirement. The separating signal is that the real amount always carries a money marker (sign, magnitude unit or currency suffix) and an account number never does. `extractAmounts` already computed `hasMoneyMarker` and discarded it; it is now returned and `selectPrimaryAmount` ranks on it. Marked tokens outrank bare ones and document order decides only within a tier, so unmarked notes such as `an trua 50000` keep their existing behaviour.
- Changed: `ExtractedAmount` is now a named type carrying `hasMoneyMarker`, the signal `extractAmounts` already computed and discarded; new exported `selectPrimaryAmount` ranks marked tokens above bare ones and returns `{ primary, ambiguous }`; `parsePasteLine` consumes it instead of `amounts[0]`, and its ambiguity flag now reflects competition within the winning tier rather than the raw token count. Tests add the eight bank formats, two `selectPrimaryAmount` unit cases and one assertion that a single marked amount is not flagged. The board and current-memory baselines are reconciled as described above.
- Result: amounts **2/8 → 8/8**. Transaction kind is unchanged at 6/8 and deliberately out of scope — the two misses (Techcombank, VietinBank) contain `CHUYEN TIEN`/`CHUYEN KHOAN`, which genuinely read as transfers. That is a separate judgement about bank vocabulary and is not claimed to be fixed here.
- The test suite was giving false confidence, and that is recorded because it matters more than the fix. The single regression fixture used `"TK ****1234 -120.000 VND"` — a **masked** account number, one of only two shapes where the leftmost token is not the account. It passed for the entire life of the parser while six of eight real formats were wrong. It is kept, because it covers the `[*#xX]` guard, and the eight real formats are added beside it. The new cases pin the amount specifically: a wrong amount is the one parser error a reviewer cannot catch by eye, since `11,004,567,890 ₫` and `250,000 ₫` are equally plausible-looking rows in a review queue.
- Blast radius, stated rather than assumed: no data was ever corrupted. Shared candidates remain pending Inbox evidence and no ledger write occurs, so the financial invariants held throughout. The defect made the feature unusable, not unsafe — the user had to correct the amount on every share, which is worse than typing it fresh.
