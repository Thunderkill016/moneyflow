# PR #496 — feat(security): publish a public security page

- Date: 2026-08-27
- Change class: Class 2 — one new public route with its own CSS Module, plus two links. No schema, migration, RPC, RLS, provider or dependency change; no ledger mutation and no new server read.
- Affected capability or project boundary: the public marketing/legal surface — a new `/security` route, linked from the landing footer and the privacy page.
- Status impact: candidate until merged. It publishes existing behaviour; no capability is added or changed.
- Lifecycle impact: completes current slice. This PR carries its own post-merge convergence: the board projection names PR #496, no successor slice is promoted, and projected current memory is updated here. `plan:resolve` intentionally reports NOT READY while this is unmerged.
- Why, from the benchmark rather than preference: YNAB, Monarch and Copilot each publish a security page; MoneyFlow did not, while already doing most of what such a page describes. It is also the cheapest of the gaps found — the content is gathered from behaviour that already exists rather than built.
- Changed: `src/app/security/page.tsx` and `src/components/security-page.tsx` with `security-page.module.css`; links added to the landing footer and the privacy page.
- The structure is the substance. Three sections — what MoneyFlow does, what the platform provides, and what does not exist — because conflating the first two is how these pages become untrustworthy: a product inherits its host's encryption and writes it as though it built it. The platform section says explicitly that those points are not ours to verify.
- The third section is the one that makes the other two credible: no independent security audit such as SOC 2, no bug-bounty programme, no third-party penetration test. Those are company-scale investments — they cost money per user or need staff to triage — and copying their appearance would be worse than the honest gap. Security pages normally omit this.
- One benchmark finding is now stated where a user can see it: Copilot publishes deletion from all internal systems including backups within 60 days, while `purge_user_tenant_data` deletes immediately with no retention window. That is the stronger position and it had never appeared on any public page.
- No contact address is invented. `SECURITY.md` already routes reports through GitHub's private advisory flow, so the page points there, and a test asserts no `mailto:` appears — a mailbox nobody owns is worse than none, which is precisely the still-open `support@moneyflow.app` problem.
- A screenshot caught a defect no test would have. The report button used `--mf-brand-text` on a brand fill; that token is a dark brand tone intended for text on normal surfaces, and every other use in the codebase is on a light background. On a brand fill it rendered blue on blue and the label vanished entirely. It now uses `--mf-on-brand`, measured in the browser at white on `rgb(3, 105, 161)`, roughly 5.9:1. Seven passing contract tests said nothing about it; rendering the page and looking is what found it.
- Presentation is owned rather than borrowed: the landing and privacy globals survive only through `presentation-ownership-baseline.json`, and adding a caller to a baselined global is the failure that rejected PR #420.
- Verified: `typecheck`, `lint` (0 errors), `test` (**1205 pass**, +7 new), `check:architecture`, `check:css-ownership`, `check:code-css-ownership` (after a real build, as that gate requires), `check:knowledge`, `test:ci-policy`, and `npm run build` with `NEXT_PUBLIC_APP_MODE=authenticated`. The page was rendered locally at 900px and reviewed, and the button's computed colours were read from the browser rather than inferred from tokens.
- Limitation, not a pass: `test:db` was not run — `agent:doctor` reports `missing required capabilities: docker`. The full `test:ui-audit:pr` was not run locally, so the page's behaviour at 320px and in dark theme rests on tokens rather than measurement. The claims about platform encryption at rest and provider backups are the provider's, repeated as such and not independently verified.
- Remaining: the `support@moneyflow.app` contact still sits on a domain owned by another company and is untouched here; it needs an address the owner controls. Retention specifics beyond account deletion remain on the privacy page rather than this one. SOC 2, bug bounty and penetration testing are deliberately unbuilt.
- Production/provider evidence: not applicable. No provider write, deployment or production-data access.
