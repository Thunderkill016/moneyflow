# PR #473 — feat(planning): carry last month's plan into an empty month

- Date: 2026-08-26
- Change class: Class 2 — bounded planning-surface action plus one domain rule and one new server action reusing an existing RPC. No schema, migration, RLS or provider change; no ledger mutation.
- Affected capability or project boundary: the `/budgets` planning surface, `src/lib/planning/budgets.ts` and `src/app/actions/budgets.ts`.
- Status impact: candidate until merged. On merge the Planning row gains a carry-forward action; no existing capability changes.
- Lifecycle impact: completes current slice. Issue #472 is registered and delivered in this same PR, which carries its own post-merge convergence: the board projection names PR #473, no successor slice is promoted, and projected current memory is updated here. `plan:resolve` intentionally reports NOT READY while this is unmerged.
- Why this next: research into what retains users in this category points at the monthly loop, not at more tracking. YNAB ships Auto-Assign and Actual Budget's envelope flow does the same, because retyping a stable plan every month is what people stop doing. MoneyFlow opened every month with zero budgets, and until they were recreated the unassigned figure from #468/#470 reported the user's whole income as unassigned — true, and useless. It also costs nothing per user, which keeps the standing cost constraint intact.
- What was already there and unused: `getBudgetsWorkspace` already loads `previousBudgets`, and the page used them only to render comparison text such as "Tăng 200.000 ₫ so với tháng trước". `upsert_monthly_budget` already exists and is already the write path for a single save. This slice therefore adds no RPC and no migration.
- Changed: `budgetsToCarryForward` in the budgets domain module derives the list to apply; `carryForwardBudgetsAction` validates that list and writes it through the same existing RPC, so budgets keep one write path rather than two that can drift; the page offers the action on the category section only when there is something to carry, recomputed from live budget state.
- The invariant the feature rests on, and it is tested twice: carry-forward is **additive only**. A category the user has already budgeted this month is never touched. Replacing a limit they set this month with last month's history would overwrite their own judgement, and they would have no way to notice it had happened. Non-positive previous limits are skipped rather than carried as zero, because `upsert_monthly_budget` treats a limit as a real cap and a zero-limit budget reads as "you may spend nothing here" rather than "not planned".
- Cases pinned by test: missing categories are carried with the target month substituted; a category budgeted in both months yields nothing; a category budgeted only this month yields nothing; zero and negative previous limits are skipped while a valid sibling is still carried; an empty previous month offers nothing; a malformed target month throws before anything is written.
- Deliberate partial-failure behaviour: a write loop that fails part-way returns what was written rather than discarding it, and the notice says how many of how many were applied. These are plans, not ledger facts, so a visible partial result is recoverable, whereas rolling back would silently undo work the user asked for. The action also rejects a list spanning more than one month or naming a category twice, so a malformed caller cannot write conflicting limits.
- Client merge rule: the applied budgets are merged into local state by category rather than replacing it, so a category edited by hand while the request was in flight keeps its own value — carry-forward never claimed that category.
