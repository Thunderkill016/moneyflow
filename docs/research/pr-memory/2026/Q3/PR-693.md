# PR #693 — Persist the unsent capture draft across dialog/tab close

- Date: 2026-09-23
- Change class: Class 2 (bounded UI/flow: one dialog, one small local store; no server, schema or money-semantics change)
- Affected capability or project boundary: manual capture resilience — `src/lib/unsent-draft.ts` (new), `src/components/add-transaction-dialog.tsx`, `src/lib/delete-account.ts`, `src/lib/unsent-draft.test.ts` (new).
- Status impact: partial → implemented. The resilience-audit Gap 3 draft-loss side of the failure path: `saveFailureMessage` already kept typed input in dialog state, but only while mounted; the failed submission is now retained in `moneyflow-unsent-draft-v1` and re-offered on next mount.
- Changed: the `!result.ok` branch writes `{kind, amount, note, payee, categoryId, accountId, occurredOn, savedAt}` (amount stays integer đồng); the success path clears it; mount hydrate restores it only while `formTouchedRef` is unset and shows `Đã khôi phục nháp chưa gửi` (info alert). Store follows the validated-localStorage convention — read validator, fail-closed drop on malformed input, registered in `LOCAL_DATA_STORAGE_KEYS` so account deletion wipes it; a `setItem` failure no-ops rather than faulting the error path.
- Design decisions: restored payee routes through `applyPayeeChange` (the `setPayee` contract test pins every payee write to that path, so saved rules still evaluate it); a still-resolvable draft category sets `categoryTouchedRef` so rule fill cannot override the reader's own last choice; unresolvable ids fall back to learned defaults rather than inventing one. Edit dialog intentionally untouched — its failure path does not use `saveFailureMessage` and it edits posted rows, not capture.
- Verified: `npm run typecheck` clean, `npm run lint` 0 errors (1 pre-existing warning in `quick-add-defaults.test.ts`, untouched), `npm run test` 1760/1760 (9 new: validator, write/read/clear lifecycle, corrupt-drop, invalid-write refusal, deletion-key registration, source-contract pins for write-on-failure and clear-on-success), `npm run build` green, `check:knowledge` pass, `test:ci-policy` 191/191, `check:css-ownership` pass (no CSS added; notice reuses `styles.formStatus`).
- Remaining: retention has no TTL — the draft lives until a successful save or account deletion, and a reader who clears a restored form still gets it re-offered on next mount (only a successful save drops it). This is draft retention, not an offline queue: nothing retries or sends on its own, and no copy claims otherwise.
- Production/provider evidence: none at open; same dialog serves demo and authenticated capture.
- Superseded issue, roadmap or claim: resilience audit Gap 3.
- Lifecycle impact: if the capture form gains fields (e.g. splits entry), extend `UnsentCaptureDraft` and bump the `-v1` key; old-shape drafts fail closed to `null` rather than hydrating partially.
