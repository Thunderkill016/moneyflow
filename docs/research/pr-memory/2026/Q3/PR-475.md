# PR #475 — feat(planning): show the reserve picture instead of only refusing with it

- Date: 2026-08-26
- Change class: Class 2 — bounded planning-surface change plus one new deterministic domain module and three narrowed server reads. No schema, migration, RPC, RLS or provider change; no ledger mutation. The arithmetic is restated, not invented.
- Affected capability or project boundary: the `/goals` planning surface, `src/lib/planning/reserve.ts` and `getGoalsWorkspace`.
- Status impact: candidate until merged. It reveals an existing enforced rule; no capability or financial semantic changes.
- Lifecycle impact: completes current slice. Issue #474 is registered and delivered in this same PR, which carries its own post-merge convergence: the board projection names PR #475, no successor slice is promoted, and projected current memory is updated here. `plan:resolve` intentionally reports NOT READY while this is unmerged.
- Why this next, chosen from measurement rather than preference: `goals.ts` was the thinnest planning module in the repository at 57 lines against 289 for budgets, 254 for allocation and 188 for commitments. Reading why turned up something better than a thin module — `adjust_savings_goal`, shipped in `20260714000600_savings_goals.sql`, already enforces `v_total_allocated + p_amount_minor > greatest(0, v_total_balance - v_recurring_reserved)` and raises `insufficient_unreserved_balance`. MoneyFlow was already computing the complete picture of what a user's money is free for, and revealing it only by refusing an action.
- What the user previously saw: `"Không đủ số dư chưa được giữ trước hoặc số tiền vượt mục tiêu."` — an error naming two possible causes and giving neither figure, with no way to see how much was free, plan against it, or tell which cause applied.
- Changed: new `reserve.ts` exporting `reservePicture`, `reservePictureFromTotals`, `fundableIntoGoals` and `reserveExplanation`; `getGoalsWorkspace` gains reads of `account_balances`, `recurring_commitment_feed` and `commitment_occurrences` for the current month, reusing the exported `mapCommitmentRow`; the goals page shows one summary item with a sentence naming every operand.
- The invariant this feature lives or dies on: **the displayed figure must equal what the RPC enforces.** Showing free money and then refusing an allocation of exactly that amount would prove the numbers cannot be trusted, which is the one claim this product rests on. Details mirrored deliberately because each could silently diverge: the `greatest(0, …)` clamp applies to balance-minus-bills **before** goal allocations are subtracted, so bills exceeding the balance cannot make goal-reserved money look available; commitments are the **current** month's from `currentMonthStart()`, matching `date_trunc('month', now())` in `Asia/Ho_Chi_Minh`, never a month being browsed; unpaid means no occurrence row rather than a flag; archived commitments and archived goals are excluded on both sides.
- That agreement is tested, not assumed: one test re-implements the RPC predicate and asserts that the exact shown amount is accepted while one đồng more is refused.
- Freshness: the goal side recomputes from live client state, so funding a goal reduces what is still free immediately rather than at the next page load. Balances and bills cannot change from that screen, so only the goal side needs to stay live — a distinction stated in the module rather than left implicit.
- Refuses to guess: when any of the three input reads fails, the figure is omitted rather than estimated, because a wrong figure here promises money the user is then refused. Demo returns null for the same reason — demo balances and commitments live in browser storage owned by other surfaces, and demo money being fictional is not a licence for the arithmetic about it to be.
- A shortfall is shown rather than clamped away: goals are funded against the balance at the time, so a later drop can leave more promised than held. The label changes to "Đã dành quá số dư" rather than relying on colour, and `fundableIntoGoals` still reports zero because a shortfall is not a fundable amount.
