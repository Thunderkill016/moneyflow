# PR #493 — chore(ci): make the knowledge contract check locally

- Date: 2026-08-27
- Change class: Class 1 — one script gains a local validation path, plus a board restructure. No application code, schema, migration, RPC, RLS, provider or dependency change. No contract is weakened: every existing rule still applies and CI still enforces the rules only it can.
- Affected capability or project boundary: `scripts/check-project-knowledge.mjs` and the ordering of `docs/plans/active/README.md`.
- Status impact: candidate until merged. No capability changes; the delivery process stops failing authors for a mistake a machine can catch.
- Lifecycle impact: completes current slice. This PR carries its own post-merge convergence: the board projection names PR #493, no successor slice is promoted, and projected current memory is updated here. `plan:resolve` intentionally reports NOT READY while this is unmerged.
- Why, from evidence rather than preference: the checker returns early unless `GITHUB_EVENT_NAME` is `pull_request`, so a PR memory record was validated for the first time on the runner. That produced **three red CI runs in one day** for one class of mistake — PR #466 and PR #483 missing `- Changed:`, and PR #484 writing `- Remaining, from the audit:` with prose before the colon. Each cost a full run for something detectable in under a second.
- What I checked before proposing a cut instead, and why I dropped it: I first intended to reduce the ten required fields, on the theory they were boilerplate. Measuring 172 records says otherwise — `Production/provider evidence: not applicable` appears in 65 and `Snapshot update: not applicable` in 67, so roughly 40% is filler and **60% carries real content**. That is not a strong enough case to weaken a contract, so the fields are untouched and the tooling is fixed instead.
- Changed: the record field, budget and snapshot checks move into a shared `validateMemoryRecord`, called by both paths; a new local path validates every PR memory record this branch touches. It reads committed changes, the working tree **and** untracked files, because a record is usually still uncommitted at the moment the check is useful — a `base...HEAD` diff alone stayed silent in exactly that case, which I found by probing rather than assuming. It exits silently where git, `main` or a merge base is unavailable, since this is early warning and CI remains the enforcing path.
- Proven, not asserted: a deliberately malformed probe record reproducing both real mistakes — a missing `- Changed:` and a `- Remaining, from the audit:` prefix — makes the local check fail with exit 1 and name both, and removing the probe returns it to 0.
- Second change, and the reason it belongs here: the board now leads with the four owner-only actions. All four are fully specified and have sat 9 to 33 days — `#40` is five checkboxes in a Supabase dashboard, `#398` has a merged runbook. They were not stalled for lack of detail; they were buried beneath NOW, NEXT, BLOCKED, OWNER DECISION and HOLD in a board whose surrounding documentation now runs to 51,837 lines against 51,237 lines of production source. Putting them first costs nothing and is the only change here that touches the actual bottleneck.
- One self-inflicted failure worth recording: `test:ci-policy` rejected the first version because my explanatory comment contained a literal gate command, and a guard forbids any script but `agent-policy.mjs` from naming one. The guard was right — it cannot distinguish prose from a second command table — so the comment was reworded rather than the guard loosened. This is the third time in one session a guard has matched my own commentary.
- Verified: `test` (**1198 pass**), `test:ci-policy` (200 pass), `check:knowledge`, `lint`, `typecheck`, `check:architecture`, `check:migrations`, and the probe described above.
- Limitation, not a pass: `test:db` was not run — `agent:doctor` reports `missing required capabilities: docker`. The local path compares against `main`, so it does nothing useful on a branch cut from elsewhere, and it cannot enforce the exactly-one-own-record rule because that needs the PR number CI supplies. Neither weakens CI.
- Remaining: the board baseline and post-merge projection ceremony is untouched. It caught no defect today and caused two of my failures, including a rebase conflict, but removing it means surgery on plan authority resolution and is a decision for the owner rather than a change to slip into a tooling fix. The wider question the board now raises — documentation at parity with production code after six weeks, 172 memory records, and four owner actions idle for up to 33 days — is recorded in the leader assessment rather than acted on here.
- Production/provider evidence: not applicable. No provider write, deployment or production-data access.
- Snapshot update: `CURRENT_PROJECT_MEMORY.md` is updated here as an explicit post-merge projection, together with the board baseline moving to `9e2c7db6` (PR #492).
- Superseded issue, roadmap or claim: supersedes the situation where a memory-record mistake could only be discovered by CI. Does not supersede `#432`, `#426` or any RRB gate.
