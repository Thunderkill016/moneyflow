## Established truth

- The existing export is a reporting artifact, not a backup: date-range filtered,
  covering 2 of 19 tenant tables, with `accounts` and `categories` absent. No
  importer or restore RPC exists anywhere in the repository.
- `purge_user_tenant_data` enumerates all 19 tenant tables and re-counts them to
  assert emptiness. The archive inventory is anchored to it, and the reverse of
  its delete order is a topological restore order verified against every foreign
  key. No foreign key is `DEFERRABLE`, so ordering is mandatory.
- Transfer balance and split exactness are enforced by the `SECURITY DEFINER`
  write RPCs, not by constraints; `transaction_entries` guarantees only
  `amount_minor <> 0`. A bulk-insert restore bypasses those invariants.
- `inbox_rules.category_id` is the one tenant foreign key that is not composite
  `(id, user_id)`. Ownership comes from `inbox_rules_validate_category`, which
  also requires `is_archived = false`.
- `transaction_entries_reconciliation_account_leg_consistent` is a
  `deferrable initially deferred` constraint trigger, checked at `COMMIT`.

## Research adopted

- PostgreSQL PL/pgSQL transaction management: an `EXCEPTION` block forms a
  subtransaction, so per-row exception handlers are forbidden in the restore body.
- PostgREST transactions: one request is one transaction and `RAISE` rolls back,
  so restore must be a single RPC; `READ COMMITTED` means idempotency needs a
  real guard.
