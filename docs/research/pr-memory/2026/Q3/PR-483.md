# PR #483 — docs(perf): record the #403 attribution result, and it is negative

- Date: 2026-08-27
- Change class: Class 0 — documentation only. No code, workflow, schema, migration, RPC, RLS, provider, dependency or financial-semantics change.
- Affected capability or project boundary: `docs/performance-budgets.md`, plus board and current-memory convergence.
- Status impact: candidate until merged. It records a measurement result and changes no capability. It does change what may honestly be claimed about the dashboard loading boundary.
- Lifecycle impact: completes current slice. The `#403` attribution result is collected and recorded in this same PR, which carries its own post-merge convergence: the board projection names PR #483, no successor slice is promoted, and projected current memory is updated here. `plan:resolve` intentionally reports NOT READY while this is unmerged.
- The loose end this closes was mine: PR #419 shipped the experiment as `workflow_dispatch`-only, and `docs/performance-budgets.md` stated that the CI-hardware run "has not been collected yet". It never was, and I recorded that in three later documents without acting on it. Run `32991729913` collected it, with 20 navigations and 10 Lighthouse passes per arm.
- Mechanism, against the criterion the document set **in advance** rather than one chosen after seeing the data: the boundary's text appeared exclusively in the arm containing it (1 of 20 versus 0 of 20), and the single low-FCP navigation is the one where it appeared. The early paint really is the loading boundary. It is also rare — one navigation in twenty, with the other nineteen reaching first paint without it at 132–184 ms. The dry run's 1-of-6 was not a small-sample artefact.
- Timing, and this is the part that matters: `/dashboard` LCP medians are 3647 ms with the boundary and 3807 ms without, a 160 ms difference in the direction the hypothesis predicts and well inside each arm's own ~500 ms range. The `/` route is a built-in control — deleting `src/app/dashboard/loading.tsx` cannot affect it, and identical script bytes (195821 B in both arms) confirm both arms built the same output for it — yet its LCP medians differ by **368 ms** between the same two arms. The noise measured on a route the change cannot touch is more than twice the effect measured on the route it can.
- Changed: `docs/performance-budgets.md` gains a result subsection under the existing `#403 FCP attribution experiment` heading, carrying the mechanism table, the timing table with the `/` control row, and the conclusion; the sentence stating that the CI-hardware run had not been collected is replaced. `docs/plans/active/README.md` and `docs/research/CURRENT_PROJECT_MEMORY.md` take the usual post-merge convergence. No other file changes.
- Conclusion recorded: the loading boundary occasionally produces an earlier first paint and has no `/dashboard` LCP effect this instrument can distinguish from noise. It is not the lever for `#403`. Keeping or removing it is a correctness and honesty decision about what a user sees during a server wait, not a performance decision, and no performance claim may be made from it in either direction.
- Written as a negative result on purpose. The evidence would otherwise sit in a run artefact that expires, and the same hypothesis would be re-argued from the same data later. Script bytes remain the only stable metric this harness has, and they are identical across arms, as they must be since a loading file changes no bundle.
- Verified: `check:knowledge`, `test:ci-policy`, `git diff --check`. No application, database or browser gate applies to a documentation-only change. The measurement itself ran on provider hardware; the numbers here are transcribed from `attribution-report.md` and cross-checked against the `modeSplit` block of `attribution-with-boundary.json` and `attribution-no-boundary.json` in the run artefact rather than taken from the report alone.
- Limitation, not a pass: one CI run on one runner. The 368 ms control figure is itself a single estimate of variance, so it bounds the effect rather than measuring the noise distribution. A second run could shift both numbers; what it is very unlikely to do is turn a 160 ms difference sitting inside a 500 ms range into a demonstrable win. The Playwright arm is unthrottled loopback and its absolute milliseconds are not comparable to the Lighthouse tables or to the 1.8 s FCP target.
