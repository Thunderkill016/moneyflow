## Phase A evidence boundary

Current production root HTML explicitly contained an image preload for `/landing/moneyflow-quick-capture.svg`. Source places that screenshot in the story section after the hero and marks only index 0 `priority`; the other story images already lazy-load. Removing that priority removes an unnecessary eager hint without changing visible layout or content. Same-harness `/` results are effectively flat, so no material landing performance win is claimed from this mechanism.

`MoneyFlowDashboard` already dynamic-imported the AddTransactionDialog and TransferDialog with `ssr: false`, but rendered both unconditionally with `open={false}` during initial hydration. Official Next guidance for deferred modals supports rendering the dynamic component only when needed so its JavaScript can be deferred. The change preserves the same handlers, account/category inputs, mutation functions and transfer handoff. The stable dashboard script-byte reduction across the Lighthouse samples is the strongest evidence that this mechanism removed initial client cost.

`AppShell` originally rendered its closed More sheet on every initial route. The first bounded attempt dynamically imported the shared `Sheet` implementation and rendered `MoreSheet` only while `moreOpen=true`. Browser/UI gates proved that immediate unmount destroyed the custom `Dialog` component before its `open=false` effect could restore focus to the trigger. The corrected implementation adds a one-way `moreLoaded` flag: initial routes still omit the Sheet; first open loads it; close changes `open` to false without unmounting it, allowing the existing dialog focus-restoration lifecycle to run. Browser smoke #3195 passed the exact assertion that previously failed.

## Remaining bottleneck and evidence gap

The dashboard LCP element remains the empty-state statement paragraph in the tested fixture. The candidate primarily reduces hydration/initial client work; it does not move dashboard LCP below 2.5 s. The root LCP is also above 2.5 s. Further optimization must be attribution-led rather than another speculative lazy-load pass.

The repository defines `npm run analyze` as `next experimental-analyze`. Official Next.js documentation supports `next experimental-analyze --output` to write static analyzer data to `.next/diagnostics/analyze`, but the current CI workflow does not execute it and the connected local container cannot resolve GitHub for a fresh checkout. This missing exact analyzer evidence is an explicit reason #527 remains open.

The connected Vercel surface exposes deployments/build/request evidence but not Speed Insights metric queries, and no preview deployment/provider write was initiated. Owner-reported performance score 39 therefore remains field provenance rather than a reproduced acceptance measurement.
