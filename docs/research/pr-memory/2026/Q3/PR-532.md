## Phase A attribution and mechanism selection

Current production root HTML showed an eager preload for the first below-fold landing story image. Source marked only that story image `priority`; removing the hint is bounded and does not change visible content. Same-harness `/` results were effectively flat, so no material landing win is claimed.

`MoneyFlowDashboard` already used `next/dynamic` for AddTransactionDialog and TransferDialog but rendered both components unconditionally with `open={false}` during initial hydration. The candidate preserves the same handlers/data authorities but mounts each dialog only while it is needed.

`AppShell` rendered closed More-sheet internals on every initial route. The first lazy attempt immediately unmounted MoreSheet when `open` became false, destroying the custom Dialog before its focus-restoration effect could run. Exact-head Chromium/WebKit CI caught the regression. The corrected one-way `moreLoaded` state still defers initial Sheet loading but keeps the component mounted after first use so the existing close lifecycle completes.

Official Next.js Bundle Analyzer guidance for 16.1+ supports `next experimental-analyze --output`, writing the route/module graph to `.next/diagnostics/analyze` for before/after diffing. #532 used that exact command on baseline and candidate rather than substituting `next build` summary numbers.

## Analyzer evidence

Baseline and candidate each emitted 83 static analyzer files under `.next/diagnostics/analyze`; the route graph includes `data/dashboard/analyze.data` plus global `data/modules.data`. Analyzer metadata size itself is not treated as user-transfer size.

The strongest module-owner change is the shared Sheet: baseline `data/modules.data` identifies `src/components/ui/sheet.tsx` as `[app-client] (ecmascript)`, while the candidate identifies the same module as `[app-client] (ecmascript, next/dynamic entry)`. That independently confirms #532 moved the closed-by-default Sheet behind a dynamic boundary.

`src/components/transfer-dialog.tsx` is a `next/dynamic entry` in both baseline and candidate, matching the pre-existing source import. Its #532 change is therefore mount/scheduling ownership, not conversion to dynamic import. `add-transaction-dialog.tsx`, `transfer-dialog.tsx`, `moneyflow-dashboard.tsx`, `app-shell.tsx` and `sheet.tsx` remain visible in `data/dashboard/analyze.data`; the analyzer describes the route/module graph including dynamic imports, so graph presence is not claimed to mean eager initial transfer. The independent Lighthouse network result supplies that delivery evidence: dashboard initial script transfer fell 319,931 -> 303,886 B while bootup/main-thread/TBT also fell materially.

This combination closes the attribution loop without inventing a bundle-size interpretation from analyzer metadata: analyzer proves the module/dynamic ownership change; Lighthouse proves the corresponding initial-browser cost reduction.

## Remaining bottleneck and closure judgment

The dashboard LCP element in the fixture remains the empty-state statement paragraph. Its element render delay fell roughly 457->214 ms, while server response was already small. The remaining cost is dominated by render-blocking CSS and residual client/main-thread work, not another unmeasured server optimization target.

#527 explicitly permits completion with LCP above 2.5 s when a material same-methodology underlying cost reduction is demonstrated and the remaining bottleneck is named. #532 meets that alternative path through script transfer, bootup, TBT and main-thread reductions, while keeping the unresolved LCP and field-score gap explicit.

The owner-reported Vercel score 39 remains field provenance. Synthetic lab improvement is not described as fixing that score. Any future performance slice must be selected again under normal plan authority rather than remaining implicitly open.
