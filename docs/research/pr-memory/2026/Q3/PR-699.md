# PR #699 — Vietnamese shorthand amounts in money inputs (50k, 1tr5, 2tỷ)

- Date: 2026-09-23
- Change class: Class 1 (bounded domain-module change in `src/lib/money.ts` + contract tests; no schema, RPC, UI-component or provider change)
- Affected capability or project boundary: `parseMoneyInput`, `formatMoneyInput` and `isFractionAttempt` in `src/lib/money.ts` — the single amount-entry contract used by capture/edit inputs.
- Status impact: candidate → implemented for shorthand parsing only. No caller-visible API change; every amount input that already goes through `parseMoneyInput` inherits the grammar.
- Changed: Vietnamese unit suffixes scale the entry to an exact integer (`k` ×10³; `tr`/`triệu`/`trieu`/`củ` ×10⁶; `tỷ`/`tỉ`/`ty` ×10⁹); post-unit digits are the unit fraction (`1tr5` = 1 500 000). Shorthand-looking entries are governed by the shorthand grammar or rejected with `NaN` — never digit-stripped into a different number. `formatMoneyInput` keeps shorthand (and half-typed unit tails like `1t`) on screen. Bare `m` stays unsupported by design. Integer-VND invariant preserved; fraction resolution uses digit strings, not floats.
- Verified: `src/lib/money.test.ts` 12/12 incl. 5 new shorthand cases (accept set, refuse set `k50`/`tr`/`1tr5x`/`1,5tr5`/`1.2.3tr`/`1tr5đ`, plain-path neutrality, on-screen retention, fraction-attempt exemption); `npm run test` 1778/1778; `npm run typecheck` clean; `npm run lint` 0 errors; `check:knowledge` + `test:ci-policy` 191/191 pass.
- Remaining: none within scope. Whether capture surfaces should *suggest* shorthand formatting (e.g. hint text) is a separate UX question.
- Production/provider evidence: none (domain module only).
- Superseded issue, roadmap or claim: none.
- Lifecycle impact: if a new unit is added to `VND_SHORTHAND_SCALE`, update `VND_SHORTHAND_UNIT`, `VND_SHORTHAND_TYPING_TAIL`, `VND_SHORTHAND_NOISE` and the tests together — the noise charset must cover the unit alphabet or letters will be cleaned off-screen.
