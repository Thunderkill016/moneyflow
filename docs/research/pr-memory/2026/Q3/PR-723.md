# PR #723 — Settings trust fixes: privacy delete log, demo deletion receipt, password entry

- Date: 2026-09-25
- Change class: fix slice — three small trust repairs across settings
  surfaces (presentation + browser-local activity log). Owner granted
  autonomous merge authority this session ("toàn quyền làm việc merge …
  ko cần hỏi ý kiến").
- Affected capability or project boundary: `/settings` hub link
  inventory, `transactions` workspace delete confirmation path, demo
  delete-account navigation. No schema, no server contract, no ledger
  semantics changed.
- Superseded issue, roadmap or claim: surface audit found three places
  where the UI's own promises were not kept.
- Status impact: the privacy page's deletion activity now reflects real
  deletes; demo account deletion lands on the explicit receipt instead
  of a landing page that discarded the outcome; the working
  `/update-password` route is reachable from settings for authenticated
  viewers only.
- Design basis:
  - `recordPrivacyDelete` existed in `privacy-prefs.ts` next to the
    already-wired `recordPrivacyExport`, but had no caller — the
    activity log claimed "Chưa có" immediately after a delete.
  - `/` reads no `deleted` search params; `src/proxy.ts` only repairs
    the outcome for the authenticated `/login?deleted=1…` path, so demo
    deletion needed to target the receipt route directly.
  - Demo has no server identity, so a password-change affordance there
    could only land on a form that cannot succeed — the link is
    `authOnly`.
- Changed:
  - `transactions-workspace.tsx`: `recordPrivacyDelete()` after a
    confirmed single delete; after bulk delete only when snapshots
    actually deleted (skipped rows do not fake activity).
  - `delete-account-page.tsx`: demo branch `router.replace` now targets
    `/account-deletion-result?deleted=1&scope=demo-local`.
  - `settings-hub-page.tsx`: `authOnly` flag on `SettingsLink`; new
    "Đổi mật khẩu" card; render filters it out for `viewer.isDemo`.
  - `settings-trust-copy.test.ts`: three contract tests pinning each
    fix (receipt route target, delete-log wiring, authOnly gating).
- Verified: 1911/1911 unit suite including new contract tests;
  typecheck; ESLint clean (one pre-existing warning in an untouched
  file); demo-browser evidence — settings hides "Đổi mật khẩu" in demo,
  a real transaction delete stamped "Xóa dữ liệu gần nhất" to
  `21:11 25/9/26`, demo delete-account landed on
  `/account-deletion-result?deleted=1&scope=demo-local` rendering the
  demo-local receipt copy.
- Remaining: authenticated `/update-password` link visibility is
  contract-tested but not browser-verified (no auth lane locally); the
  e2e auth path covers the route itself.
- Production/provider evidence: none — client-side surfaces only; no
  provider or production-data write was touched.
