# PR #427 — refactor: simplify the default daily path

- Date: 2026-08-18

- Status impact: candidate only; not durable project truth until merged.
- Base: `main@fec11958a573653ebb706d4c3307ace6c7d2d4ac`.
- Owner direction: remove things that make the product worse and prefer simple, proven, high-impact improvements. This PR is deliberately one bounded slice rather than an open-ended cleanup/refactor.

## Candidate change

1. **One desktop capture primary.** `AppShell` stops rendering the `PRIMARY_NAV` action in the desktop sidebar. The existing topbar `Ghi chi tiêu` remains the desktop primary. Mobile still derives its five-slot dock from `PRIMARY_NAV`, keeps the centered `Ghi`, and invokes `resolvedMobilePrimary` exactly as before.
2. **Retire the redundant shell capture chooser.** Once the desktop sidebar action is gone, no shell caller needs the `CaptureSheet`; its state, `CAPTURE_OPTIONS` import and component are removed rather than left as unreachable client code.
3. **Progressive-disclose detailed planning.** `/dashboard` stops rendering `DashboardPlanningColumn`. `DashboardHeaderSections` still contains compact Planning links and every dedicated planning route remains. The daily dashboard keeps balances/totals, attention signals, categories and recent transactions.
4. **Stop serializing hidden planning detail.** `/dashboard/page.tsx` no longer passes income templates or goals into the client dashboard because the removed planning column was their only home consumer. Budgets and commitments remain because the attention strip genuinely uses them.

## Authority and research basis

Repository authority came first: `AGENTS.md` and product principles require the smallest coherent slice, one primary action per viewport, a daily-ledger core and progressive disclosure for secondary capability. Existing #419 cross-device evidence showed both `Nhập nhanh` in the desktop sidebar and `Ghi chi tiêu` in the topbar simultaneously. Existing #403 performance evidence names dashboard hydration/client-JS/main-thread cost as a repository-controlled bottleneck (~311.6 KB transferred script and ~766–814 ms JS bootup while server response is ~14–15 ms).

External primary research is supporting rationale only:

- GOV.UK/GDS: Do less; Design with data; Do the hard work to make it simple.
- Hick (1952) and Hyman (1953): choice/reaction time rises with choice information/uncertainty; used narrowly to justify removing unnecessary simultaneous choices.
- Next.js App Router docs: Server Components do not add client JS and client boundaries should be limited to interactive surface.

Repository behavior/tests outrank those general principles.
