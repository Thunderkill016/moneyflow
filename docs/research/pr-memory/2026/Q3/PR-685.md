# PR #685 — Explicit adjustment transaction closes nonzero reconciliation difference

- Date: 2026-09-23
- Change class: Class 3 (financial/data — a new ledger-writing path inside the privileged `security definer` reconciliation boundary)
- Affected capability or project boundary: `supabase/migrations/20260923013000_reconciliation_adjustment_completion.sql` (redefines `complete_account_reconciliation` with `p_adjustment_category_id`/`p_adjustment_note`/`p_adjustment_payee`, old signature dropped per precedent), `src/app/actions/reconciliation.ts` (schema + payload + error mapping), `src/components/account-reconciliation-page.tsx` (adjustment `Dialog` with forced-kind `SelectField`, fixed-label preview, optional payee; demo register now hydrates from `readStoredTransactions()`), `src/app/accounts/[accountId]/reconcile/page.tsx` (categories plumbing), `src/lib/reconciliation.ts` (`reconciliationAdjustmentNote`/`reconciliationAdjustmentKind`, `completeDemoAccountReconciliation` returns `adjustmentTransaction`), pgTAP `account_reconciliation_adjustment.test.sql` (+33 assertions), signature pins in `account_reconciliation_current_main`/`account_reconciliation_locking` tests, e2e spec reworked for the adjustment flow.
- Status impact: a nonzero statement could previously never complete — `reconciliation_difference_nonzero` hard-failed. Now the user may explicitly close the gap with a category-chosen adjustment posted as a real locked transaction dated on the statement date.
- Changed: the RPC inserts the adjustment transaction + entry atomically inside the existing account lock (kind forced by difference sign — income when statement > cleared, expense when below), lands the entry `reconciled` with `reconciliation_id`/`cleared_at` set, recomputes the snapshot to zero before completing, and records the REAL pre-adjustment difference in the `completed` event (previously hardcoded 0). Idempotency key is `md5(reconciliation_id || ':reconcile-adjustment:' || prior_completed_event_count)::uuid` — deterministic and safe across reopen → recomplete cycles. Category validation reuses `category_kind_mismatch`/`category_archived`; `note_too_long`/`payee_too_long` mirror `create_money_transaction`. Completion events, reopening and leg consistency all reuse existing machinery unchanged. Zero-difference completion and the no-category nonzero failure are preserved byte-for-byte in behavior.
- Verified: `check:migrations` (baseline `--write` for the new migration), `typecheck`, `lint` (1 pre-existing warning in unrelated `quick-add-defaults.test.ts`), `npm test` (1660 pass incl. new demo + contract tests), `build`, `check:knowledge`, `test:ci-policy` (191), `check:architecture`, `check:css-ownership`, `check:capabilities`, `check:deployment-env`, `git diff --check`.
- Remaining: pgTAP (33 assertions) and the e2e spec were written and hand-reviewed but run only in CI — no local Docker/Podman or browser runner exists in this environment. Assertion counts were hand-verified against `plan(33)`. The shipped UI never sends `p_adjustment_note` (fixed system label only); the parameter exists for contract completeness.
- Production/provider evidence: none — migration applies at deploy; post-merge production verification remains an owner decision.
- Superseded issue, roadmap or claim: none.
- Lifecycle impact: reopen → recomplete emits a second `completed` event and a second adjustment only when the difference is again nonzero; if the prior adjustment leg is still cleared the recompletion needs no new adjustment. Future adjustment metadata (e.g. richer audit trail fields) can extend the event row without touching this path.
