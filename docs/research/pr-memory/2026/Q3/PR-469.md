# PR #469 — feat(planning): show money that has not been given a job yet

- Date: 2026-08-26
- Change class: Class 2 — bounded planning-surface change plus one new deterministic domain module and one narrowed server read. No schema, migration, RLS, RPC or provider change; no ledger mutation of any kind.
- Affected capability or project boundary: the `/budgets` planning surface and `getBudgetsWorkspace`. Adds `src/lib/planning/allocation.ts`.
- Status impact: candidate until merged. On merge the Planning row of the capability inventory gains a stated unassigned figure; no existing capability changes.
- Lifecycle impact: registers and delivers issue #468 as a bounded slice. This PR carries its own post-merge convergence, so `plan:resolve` intentionally reports NOT READY while it is unmerged.
- Why this and not more acquisition work: measured against MoMo, Money Lover, MISA and YNAB, MoneyFlow's budgeting was the commodity feature all four already ship — category caps, over-limit alerts, charts. `BudgetSummary` was `{ categoryId, monthStart, limit, spent }`, and `grep` found no "unassigned"/"chưa phân bổ" anywhere in `src/`. The rows where YNAB differs are exactly the rows nobody in the Vietnamese market occupies, and they are the documented reason YNAB retains users for years while free trackers are abandoned after weeks. It also satisfies the cost constraint absolutely: pure arithmetic on data already present, no API, no licence, no per-user fee.
- Changed: new `allocation.ts` exporting `monthIncomeTotal`, `allocateMonthFromTotals`, `allocateMonth` and `allocationExplanation`; `getBudgetsWorkspace` gains a narrowed `transaction_feed` read selecting only `amount_minor` for `kind = income` inside the selected month, summed through a safe-integer helper, with demo income derived from the same demo ledger the demo dashboard reads; `BudgetsWorkspace` and the page's workspace type gain `monthIncome`; the budgets page adds one `PlanningSummaryItem` to the existing summary, recomputing the figure from live client budget state so it moves as limits are added, edited or removed.
- Correctness traps addressed, each covered by a test: income is selected byte-identically to `calculateDashboardSummary` (`kind === "income"` over `occurredOn.startsWith(monthPrefix)`), and a test asserts the two agree, because two different incomes for one month on two screens would destroy the figure's credibility; a whole-month prefix is used rather than a window ending today, so an income row dated later this month stays inside both figures; transfers are excluded by matching `kind` exactly, since counting one would invent money that was already there; other months' budgets and last month's income are filtered out; a malformed month throws rather than silently reporting zero, which would read as "nothing assigned" instead of "the question was invalid".
- Boundaries held deliberately: **recorded income only**, never income templates, because templates are expectations and `PRINCIPLES.md` puts facts before derived views. **No carry-over between months** — YNAB's "age your money" rule assumes a stable salary, and the merged Vietnam strategy explicitly records that irregular-income users need their own observed workflow rather than being treated as a variant of salaried behaviour. Carry-over remains a separate decision.
- The advice line, guarded rather than asserted: this states arithmetic on the user's own recorded numbers and leaves the decision to them. A vocabulary test runs `allocationExplanation` across five states and fails on `nên|đừng|hãy|cảnh báo|vượt mức|tiết kiệm|cắt giảm|quá nhiều|hạn chế|khuyên|cẩn thận|coi chừng|còn có thể tiêu`, so the wording cannot drift into the spending guidance the product withdrew.
- Over-allocation does not rely on colour: the label itself changes to "Phân bổ vượt thu nhập", and the explanation names both operands so the reader can check the subtraction.
