# PR #502 — publish a mailbox the owner can actually read

- Date: 2026-08-27
- Change class: Class 2 — user-facing published contact plus one new domain module and a repository-wide guard. No schema, migration, RPC, RLS, provider or financial-semantic change; no ledger value or calculation touched.
- Affected capability or project boundary: the published support/privacy contact, the canonical production origin constant, and two release-readiness gates closed by owner decision.
- Status impact: candidate until merged. On merge the product publishes a contact the operator can read, which it never did before.
- Lifecycle impact: authority transition. No slice is completed or promoted — none is registered. It carries the board's move to PR #501's merged commit `855f23ac`, the transition this PR is the same-PR projection for.
- The defect in one sentence: `support@moneyflow.app` sits on `moneyflow.app`, a domain this project does not own and which serves a different Money Flow product operated by another company, so every privacy request and every in-app error report a user sent went to a stranger's mailbox and the owner never learned that anyone had asked for help.
- Changed: `src/lib/support-contact.ts` and `src/lib/support-contact.test.ts` added; `src/components/privacy-policy-page.tsx` and `src/components/route-error.tsx` now read the single constant instead of each holding its own copy; `src/lib/privacy-policy-copy.test.ts` updated; `docs/plans/active/README.md` and `docs/research/CURRENT_PROJECT_MEMORY.md` record the two owner decisions.
- The address was duplicated across two unrelated components, which is how it drifted out of anyone's attention. It now lives in one module, and `support-contact.test.ts` walks every `.ts`/`.tsx` file under `src/` and fails on any address whose host is not owned. Hosts reserved by RFC 2606 for documentation and testing — `example.com`, `.test`, `.invalid`, `.localhost` — are exempt because they can never reach a real mailbox, and the host regex requires an alphabetic final label so provenance version strings like `csv_import@2.0` are not mistaken for addresses.
- `PRODUCTION_ORIGIN` is `https://mfvn.vercel.app`, taken from the Vercel project's own domain list rather than assumed. `moneyflow-vn.vercel.app` is no longer attached to the project and only redirects; `moneyflow.app` was never ours.
- Verified: `typecheck`, `lint`, `check:architecture`, `check:css-ownership`, `check:code-css-ownership`, `test:ci-policy` all exit 0; `npm test` **1224 pass, 0 fail** (+4); `npm run build` exit 0. Proven by rendering rather than by reading source: the built demo server returned `mailto:dinhbahoang1605@gmail.com` on `/privacy`.
- Proven to fail, not only to pass: restoring `support@moneyflow.app` into `route-error.tsx` turned the guard red naming that file and address, exit 1. It was then restored.
- One existing test changed, and the reason matters. `privacy-policy-copy.test.ts` pinned the literal address string in the published policy — that pinning is precisely how an unreadable address survived in user-facing text. It now pins the source (`SUPPORT_EMAIL`), so the page must still publish a contact while the guard above owns the value.
- **RRB-05 closed by owner decision, 2026-08-27.** What is proven is that the operator can read the mailbox. No claim is made that a personal Gmail address is the right long-term support channel, and publishing it in a public repository exposes it to address scraping — an accepted cost of the decision, not an oversight.
- **RRB-02 closed 2026-08-27 by the explicit owner limitation decision the gate always allowed**, and this record corrects an overstatement I made earlier the same day. I ranked hosted restore first and called it the product's least-proven promise. That was wrong: `supabase/tests/database/restore_user_archive.test.sql` runs **42 pgTAP assertions over 464 lines** against the real `restore_user_archive` function on every CI run — confirmed in run 33066820310 — covering removal reverting the overwritten profile, a bad restore staying recoverable, and a corrected restore rebuilding the ledger, alongside 19 archive-contract unit-test files. What stays unexercised is narrower than the gate's name: the managed-Supabase path only.
- Remaining: the managed-Supabase restore path — extensions, roles, `security definer` behaviour, timeouts on a large archive — is an accepted limitation and not proof. A personal mailbox has no shared inbox, no aliasing and no handover path. Historical PR-memory records and `RELEASE_READINESS_AUDIT_V1.md` still contain the old address and were deliberately left alone: they are evidence of what was true when written, and rewriting them would destroy the record of the defect. Separately, the Vercel project builds production on **Node 24.x** while PR #498 pinned the repository to 22 in `engines`, `.nvmrc` and CI — three declarations, none matching what actually ships; out of scope here and reported rather than fixed.
- Production/provider evidence: the Vercel project's domain list and Node version were read through the provider API. No provider write, no deployment, no production-data access.
- Snapshot update: `docs/research/CURRENT_PROJECT_MEMORY.md` and the board move to PR #501's baseline `855f23ac`, carry the PR #502 projection, and record RRB-02 and RRB-05 as closed with their limitations stated.
- Superseded issue, roadmap or claim: supersedes RRB-05's open state and RRB-02's open state, and supersedes my own earlier ranking of hosted restore as the largest unproven claim.
