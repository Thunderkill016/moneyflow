# PR #497 — feat(observability): send client errors somewhere a person will read them

- Date: 2026-08-27
- Change class: Class 2 — one new public API route, one client delivery path, one domain module. No schema, migration, RPC, RLS, provider or dependency change; no ledger mutation and dependencies stay at 17.
- Affected capability or project boundary: client error reporting — `src/lib/safe-log.ts`, a new `src/lib/client-error-report.ts`, and a new `POST /api/client-error`.
- Status impact: candidate until merged. On merge, a production defect becomes visible to the operator for the first time; no user-facing capability changes.
- Lifecycle impact: completes current slice. This PR carries its own post-merge convergence: the board projection names PR #497, no successor slice is promoted, and projected current memory is updated here. `plan:resolve` intentionally reports NOT READY while this is unmerged.
- Why this first among the engineering-benchmark gaps: `logClientError` wrote to `console.error` in the browser, so a user hitting a bug saw an error screen, closed the app, and nobody ever found out. That mattered little while nobody used the product; it started mattering on 2026-08-27, when the owner used it on a real phone.
- The decision not to add a vendor, which is the substance of the change: an error-tracking service would mean a new dependency, a new data processor to disclose on the privacy page, and a finance app's error payloads leaving for a third party. Posting to an own route puts the report in the deployment platform's runtime logs instead — no new processor, nothing new to disclose, and the dependency count stays at 17, which the same benchmark noted is unusually low and worth protecting.
- Half the work already existed and was found by reading rather than assumed: `safe-log.ts` redacts statement text and thirty-odd sensitive field names, and its own comment states it runs before "console / APM / third-party sinks". `trackProductEvent` is documented as a no-op sink awaiting a provider. The gap was a sink, not sanitisation.
- Changed: `client-error-report.ts` builds and re-sanitises reports with hard caps; `logClientError` additionally delivers through `navigator.sendBeacon`, falling back to `fetch` with `keepalive`; `POST /api/client-error` re-sanitises and writes one structured line to the server console.
- My first design was wrong and a unit test caught it. `redactForLog` redacts by **key name** as well as by content, and its sensitive list contains `"message"` — so passing an error as `{ name, message, digest }` redacted every message unconditionally. The reporter would have shipped `"[redacted]"` for a plain `TypeError` forever while appearing to work. Fields are now sanitised as strings, which keeps the content rule and drops the key rule.
- A second correction, to my own expectation rather than the code: I expected a 5,000-character field to be truncated to the 300-character cap. The real behaviour replaces it outright, because a 300-character excerpt of someone's statement is still their statement. The test now asserts the safer real behaviour instead of the weaker one I assumed.
- The server does not trust the client, and that is deliberate rather than defensive habit: the route is public because errors happen before and outside authentication, so anything at all can be posted to it and whatever is posted lands in retained logs — a worse leak than the browser console it replaces. It re-sanitises everything, caps the body before parsing, and answers 204 in every case so an attacker learns nothing and reporting an error never produces one.
- Delivery uses `sendBeacon` because an error frequently precedes a navigation or reload, and a `fetch` started at that moment is cancelled with the document — losing the report exactly when it matters most.
- Verified: `typecheck`, `lint` (0 errors), `test` (**1213 pass**, +8 unit), `check:architecture`, `check:css-ownership`, `check:code-css-ownership`, `check:knowledge`, `test:ci-policy`, `check:migrations`, and `npm run build` with `NEXT_PUBLIC_APP_MODE=authenticated`. Two browser specs were run locally, and the server's own log line from that run reads `[client-error] {"context":"e2e","name":"Error","message":"[redacted]","route":"/transactions"}` — a bank statement went in as the message and came out redacted, and `?category=Ăn uống` was stripped, which matters because this product puts category and account names in query strings.
- One test was deleted rather than kept: a browser case asserting `Array.isArray(posted)`, which is true whether or not anything was ever sent. A vacuous assertion reads as coverage and is worse than no test.
- Limitation, not a pass: `test:db` was not run — `agent:doctor` reports `missing required capabilities: docker`. The `sendBeacon` delivery path cannot be forced deterministically from Playwright, so that half rests on unit tests and the observed server log line rather than on an automated browser assertion. The route has no rate limiting beyond a size cap; it is unauthenticated by necessity and a determined caller can fill logs with well-formed reports.
- Remaining, from the same benchmark and untouched here: no `LICENSE` on a public repository, which defaults to all rights reserved; no versioning — `0.1.0` after 521 commits with zero tags and zero releases, so a user report cannot be tied to a build; Node version unpinned by `engines` or `.nvmrc`; no uptime or health check.
