# PR #669 — Due recurring commitments surfaced as Inbox suggestions

- Date: 2026-09-22
- Change class: Class 2 (bounded UI/flow — new reviewable suggestion path over existing domains)
- Affected capability or project boundary: `src/lib/planning/commitment-suggestions.ts` (new pure builder + id format `commitment:<id>:<monthStart>` + edit guard), `src/lib/demo/commitment-fixtures.ts` (extracted client-safe demo seeds), `src/app/actions/commitments.ts` (`listDueCommitmentsAction`), `src/server/commitments.ts` (seed extraction), `src/server/inbox.ts` (badge count includes due-unpaid), `src/components/inbox/inbox-page.tsx` (virtual merge, commit-gated approve branch, bulk filtering), `src/lib/inbox/candidate-store.ts` + provenance/review/reconciliation maps (`"commitment"` source).
- Status impact: closes the Stage-1 "low-maintenance reality" gap where recurring commitments required opening Commitments and pressing pay each cycle. - Changed: due, unpaid, active commitments appear as virtual Inbox candidates; approving routes through the existing atomic `pay_recurring_commitment` RPC/local path — no auto-post, no new ledger mutation path, no migration (suggestions are regenerated per load and never persisted). Bulk reject/category/account strip suggestion ids; review panel skips server-plan lookup for non-UUID ids; edit guard allows only the paid-on date.

Real burden reduction (pay-from-Inbox vs pay-from-Commitments) is measurable via existing `candidate_approved` source prop but needs usage data.
- Production/provider evidence: none (virtual candidates; browser smoke delegated to CI lanes).
