# PR #499 — meet WCAG 2.2 AA across the ledger, and gate it

- Date: 2026-08-27
- Change class: Class 2 — bounded presentation change across many surfaces plus one new browser gate. No schema, migration, RPC, RLS, provider or financial-semantic change; no ledger value or calculation touched.
- Affected capability or project boundary: colour tokens, the shared Button/Alert/Toast primitives, the app-shell link reset, and the cross-device audit suite.
- Status impact: candidate until merged. On merge the product meets the same accessibility conformance level its commercial comparators publish, and a gate keeps it there.
- Lifecycle impact: none. No current agent-executable slice was registered, so this claims no slice and promotes none; the board baseline is unchanged.
- Measured before changing anything: axe-core 4.13 run with only the WCAG 2.2 AA tag set across 22 demo routes reported **24 violations across 5 rules**. After the change the same engine reports **0 across 22 routes × 2 themes × 2 viewports (88 page-scans)**.
- The standard is not one I invented. YNAB's published accessibility statement names "EN 301 549 v.3.2.1 and WCAG 2.2 Level AA"; that is the tag set scanned. Best-practice rules outside conformance are deliberately excluded, because failing a build on advice teaches people to ignore the build.
- Changed: 33 `color:` declarations across 12 CSS Modules moved from a fill token to its existing `-text` variant; `--mf-on-expense` added to `document-theme.css` for both themes; the app-shell link reset now excludes `[data-slot~="button"]` and `[data-slot~="link-button"]`; `text-destructive` replaced in `button.tsx`, `text-field.tsx` and `select-field.tsx`; the 85% opacity removed from `AlertDescription` and toast descriptions; `aria-label` added to the dashboard goal progressbar; the reports category bars made decorative; the reports trend scroller made keyboard-reachable with its own focus ring; the onboarding `<ol role="progressbar">` conflict resolved; `e2e/audit/wcag.audit.spec.ts` added and registered as the `chromium-wcag` audit project inside `test:ui-audit:pr`; `axe-core` added as a devDependency; `SAFE-06` updated.
- Four root causes, each systematic rather than local. Fill tokens (`--mf-income`, `--mf-expense`, `--mf-warning`) were used as text colour in 33 places while a correctly-graded `-text` variant already existed for every one of them — the design system had the answer and the callers did not use it. `.shell :where(a) { color: inherit }` carries the same specificity as `.text-primary-foreground`, so source order decided it and every primary-styled `<a>` inside the shell painted near-black on the brand fill at 2.99:1; CDP matched-rule inspection found it, not reading. Literal `white` on `--mf-brand` and `--mf-expense` fails in dark because both fills flip light there — 2.14:1 and 2.77:1 — which is why `--mf-on-brand` exists and why `--mf-on-expense` had to be added. And `role="progressbar"` on an `<ol>` overrides the implicit list role, so the `<li>` children were already unreachable before axe named them.
- Verified: `typecheck`, `lint`, `check:architecture`, `check:css-ownership`, `check:code-css-ownership`, `test:ci-policy`, `check:migrations` all exit 0; `npm test` **1220 pass, 0 fail**; the new `chromium-wcag` project **38 passed in 58.5s**; `npm run build` exit 0. Production measured with Lighthouse 12 on the deployed build: mobile LCP 2.4 s, CLS 0, TBT 140 ms, scores 96 / 100 / 100 / 100.
- The gate was proven non-vacuous rather than assumed: reverting one token to its fill grade turned the light-theme test red and left the dark-theme test green, which is the correct asymmetry because the dark token already met the threshold. It was then restored.
- `networkidle` is not used and cannot be. Next prefetches every `<Link>` entering the viewport, so on link-dense routes the network never idles — `/reports` and `/timeline` each hung the full 45 s timeout before the wait was changed to the app's own `main:not([aria-busy="true"])` signal, which is a real readiness condition rather than a guessed delay.
- One existing test had to change, and it is worth naming plainly. `SAFE-06` pinned `.legendIncome` to `var(--mf-income)` — the exact token measured at 3.30:1. Its stated intent, that semantic colour stays on the figures, is unchanged; what changed is which token it pins, not whether it pins one.
- Remaining: only demo mode was scanned, so surfaces reachable only with a real account are unmeasured. axe covers roughly half of WCAG's success criteria by Deque's own account and replaces no human review — screen-reader order, focus order and label meaning still need a person. `brand-lockup.module.css` keeps a hard-coded `#ffffff` for a `tone="inverse"` variant that currently has no caller; it was left alone rather than changed blind. No accessibility statement is published, which every comparator has.
- Production/provider evidence: not applicable to the change. Production was read for measurement only — Lighthouse against the deployed build and `/api/health` — with no write, deployment or production-data access.
- Snapshot update: none. `Lifecycle impact: none`, no capability row changes and no board baseline movement.
- Superseded issue, roadmap or claim: supersedes the implicit claim that the 14-viewport cross-device audit covered accessibility. It measured layout, text scaling and keyboard reach across devices and never ran a WCAG rule engine, which is why 24 conformance failures survived it.
