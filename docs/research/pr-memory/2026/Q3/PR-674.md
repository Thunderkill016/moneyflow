# PR #674 — Recurring ledger patterns detected as reviewable commitment suggestions

- Date: 2026-09-22
- Change class: Class 2 (bounded UI/flow — new reviewable suggestion surface over the existing ledger read path)
- Affected capability or project boundary: `src/lib/planning/recurring-detection.ts` (new pure detector + suggestion types + 12-month window helper), `src/lib/planning/recurring-dismissals.ts` (new localStorage dismissal store keyed by `expense|<normalized note>` hash), `src/server/commitments.ts` (advisory paginated `transaction_feed` read for auth mode), `src/app/commitments/page.tsx`, `src/components/planning/commitments-page.tsx` (suggestion section, dismiss/create actions), `src/components/planning/commitment-dialog.tsx` (`draft` prefill prop), `src/lib/delete-account.ts` (dismissal key added to the local-data wipe).
- Status impact: closes the Stage-1 discovery gap where recurring bills had to be noticed and declared fully by hand. Detection proposes; the ledger only changes when the user reviews and saves through the existing commitment path — complements #669 (declared commitments surfaced in Inbox) rather than duplicating it.
- Changed: /commitments shows up to 5 suggestion cards for expense notes recurring in ≥3 distinct months with ~monthly chain gaps, ±10% median-amount tolerance, circular day-of-month coherence, a density bound rejecting weekly cadences and a ~2-cycle recency window. "Tạo khoản định kỳ" opens the existing dialog pre-filled as a create draft (no id); "Bỏ qua" dismisses by stable key. Declared commitments suppress matching suggestions; saving a suggested draft records the key as handled. Demo mode detects over the localStorage ledger; auth mode over a bounded server read. No migration, no new write path.
- Verified: recurring-detection.test 21/21, recurring-dismissals.test 4/4, full suite 1549/1549, typecheck, lint (1 pre-existing warning), build 51 routes, check:knowledge, ci-policy 191/191, css-ownership, architecture, capabilities.
- Remaining: suggestions are proposals only — no auto-create or scheduling by design. Detection rows are loaded at page render (no live refresh after new transactions until reload). Dismissals are device-local, not synced. Auth-mode read cost is a bounded extra query per commitments-page load.
- Production/provider evidence: none (advisory read on an existing security_invoker view; browser behavior delegated to CI lanes).
- Superseded issue, roadmap or claim: none.
- Lifecycle impact: if suggestion acceptance is high, the detector thresholds (MIN_PATTERN_MONTHS, tolerances) may warrant tuning toward recall; if dismissal churn is high, revisit grouping normalization or add a suppression reason. A future sync of dismissals across devices would need an owner-approved durable store.
