# PR #724 — Opt-in passphrase encryption for downloaded backups

- Date: 2026-09-25
- Change class: feature slice — new pure crypto module, one added
  filename helper, presentation wiring on `/settings/backup`. Owner
  granted autonomous merge authority this session ("toàn quyền làm việc
  merge … ko cần hỏi ý kiến").
- Affected capability or project boundary: backup file transport format.
  The archive document itself, the RPCs, the validators and the server
  actions are untouched — encryption is an opt-in envelope around the
  same bytes.
- Superseded issue, roadmap or claim: backlog item "Backup: encrypted
  backup option (client-side AES-GCM)".
- Status impact: a backup can now be sealed before it lands in a
  downloads folder or cloud drive; opening it back up needs only the
  passphrase on the same page. Plain archives remain the default and
  round-trip identically.
- Design basis:
  - Web Crypto (PBKDF2-SHA-256 250k → AES-256-GCM): zero new dependency,
    secure-context native, and authenticated — a wrong passphrase and a
    tampered file fail as one `decrypt_failed`, which is the only honest
    thing the crypto can say.
  - JSON envelope over a binary container: keeps the file
    self-describing, reuses the `.json` pickers, and lets a wrong tool
    still report what it is looking at.
  - `…-ma-hoa-…` filename discloses encryption — a sealed file named
    like a plain archive would read as corruption.
  - Decrypted bytes re-enter the *same* `ingestArchiveBytes` /
    `verifyArchiveBytes` boundary: an envelope cannot smuggle a weaker
    archive format past the validators.
  - Passphrase stays page-local: `createArchiveBackupAction` returns the
    archive document; sealing happens in the component after it.
    Contract test asserts server action source contains no passphrase.
- Changed:
  - `src/lib/archive/backup-encryption.ts` (new): envelope detection,
    `encryptBackupBytes`, `decryptBackupBytes` with typed failure codes;
    fresh 16-byte salt and 12-byte IV per seal.
  - `src/lib/archive/archive-backup.ts`: `encryptedBackupFileName`.
  - `backup-settings-page.tsx`: opt-in checkbox + ≥8-char passphrase
    gate on create; `needsPassphrase` state on restore and verify
    pickers; shared `acceptPlainBytes`/`acceptVerifyPlainBytes` so both
    entries cross identical ingress.
- Verified: domain tests 7/7 (round-trip, fresh salt/IV, wrong pass,
  tamper, malformed envelope, empty pass); archive tests 31/31

  191/191; build 52/52 routes; demo-browser evidence — encrypted file
