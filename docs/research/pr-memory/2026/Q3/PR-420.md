# PR #420 — feat(dashboard): open a category figure to the rows behind it

- Date: 2026-08-18
- Change class: Class 2 — bounded UI/flow on the canonical dashboard plus one new domain module. No schema, RLS, Auth, provider, CI or financial-semantics change; `get_dashboard_bundle` is untouched and remains a single bounded RPC with no shared cache.
- Affected capability or project boundary: canonical `/dashboard` presentation and the `/dashboard` → `/transactions` path. Ships the traceability half of the Phase D brand mechanism, which was previously recorded as a target rather than shipped: before this branch the dashboard contained **zero links**.
- Status impact: candidate. Product work, unrelated to #403/#415 performance work. Does not touch RRB-08 or any release gate.
- Changed: added `src/lib/dashboard-drilldown.ts`, which derives a whole-calendar-month window from the server-resolved `workspace.today` and builds `/transactions` links through the existing `transactionFilterSearch` serializer; wired category rows in `dashboard-overview-sections.tsx` to that builder with a full-row overlay link; added the supporting CSS; passed `today` down from `moneyflow-dashboard.tsx`. Added `docs/plans/PRODUCT_DEVELOPMENT_PLAN.md`, a whole-project plan marking done, in-progress, not-started and externally-blocked work.
- Correctness traps found by reading current code, each now covered by a test: the month aggregates select on `occurredOn.startsWith("YYYY-MM")`, so a window ending at `today` would have dropped rows dated later this month that the dashboard already counted; the window must come from the server date, not a client clock, or a reader near midnight or in another timezone opens a different month than the figure they clicked; `/transactions` resolves `category` **by name** and falls back to showing everything when it does not match, so a row without a usable name renders as plain text rather than a link that opens the whole ledger while looking like one category.
- Guarantee boundary, stated rather than implied: kind-level totals are an **exact sum** of the drilled rows. Category views are a **set-membership** answer, because a split row is genuinely behind a category share while the share counts only its line and the ledger shows the whole transaction. The test asserts that difference so the stronger claim cannot later be made in the UI. Net (thu−chi) is deliberately **not** linked, since no single row set sums to a net figure.
- CI caught two real defects in this branch, both mine. `check:code-css-ownership` rejected the overlay as a new global class styled only under someone else's ancestor — I had run `check:css-ownership` locally but not that gate, and the fix was to give the class a real CSS Module owner rather than add it to the baseline. Then the cross-device audit caught the 44px target regression described above. Both are recorded because a green PR that needed two rounds of gate feedback is weaker evidence of care than one that did not.
- Verified: 10 pure-function invariants in `src/lib/dashboard-drilldown.test.ts` covering exact-sum expense/income, the later-in-month row, transfer neutrality on both sides, last month not leaking, category set membership, the split caveat, refusal to emit a link without a resolvable category, href round-trip, and month-end maths for February, leap February and December. Browser proof in `e2e/dashboard-drilldown.spec.ts`: records a real expense through the capture flow, clicks the row, asserts the emitted window/kind/category survive into workspace filter state and that the target is ≥44px. Local `test` (1083), `lint`, `typecheck`, `check:css-ownership`, `check:architecture`, `check:knowledge`, `test:ci-policy`, `check:migrations` and `git diff --check` all pass. Exact-head provider checks are authoritative.
- Also shipped in this branch: the featured budget panel now opens its category's rows for the budget's own month (Phase 1.4), keyed on `monthStart` rather than today because a budget period is not necessarily the current month. It renders as an explicit 44px-compliant `section-link` rather than an overlay, chosen deliberately after the legend collision below. The drill-down parameter was renamed `today` → `withinMonth` so that carrying a budget month is honest rather than a misuse of a field documented as the current date. Phase 1.3 (account balances) turned out to need no work: the dashboard shows only a total balance with no per-account rows, and `/accounts` already links each account to its register — the plan entry claiming otherwise was my error and is corrected.
- Month drill-down landed after all, at reduced scope (Phase 1.2). I had recorded it as blocked on a statement-density decision; that framing was wrong, because it assumed each figure had to become its own 44px target. The period row above the legend was already a two-column flex holding a single child, so an explicit link lands where the layout expected it and the legend keeps its density. It is **deliberately unfiltered by kind**: the statement shows income, expense and a difference, and no single list sums to all three, so carrying a kind would claim a correspondence that does not exist. Per-figure drill-downs remain undone and would still need the density decision I described.
- Remaining: per-figure income and expense drill-downs. Month totals (Phase 1.2) were wired and then **reverted inside this PR**: the cross-device audit failed `dashboard keeps every pressable control at least 44×44px` at 320px, because the statement legend is a `flex-wrap` row with an 8px row gap and a compliant target there would overlap its neighbours. Reverted rather than forced through, since fixing one accessibility rule by breaking another is not a fix; shipping it needs the legend given real height, which is a density decision about the statement card. Demo mode starts with an empty ledger, so the category panel does not render until something is recorded — that first-run gap is recorded as Phase 1.7 and is not addressed here.
