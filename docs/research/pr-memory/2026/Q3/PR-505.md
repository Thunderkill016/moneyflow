# PR #505 — one capture primary on desktop, and a real home for the rest

- Date: 2026-08-27
- Change class: Class 2 — bounded navigation and presentation change across the app shell and the Inbox page, plus removal of an unreachable component. No schema, migration, RPC, RLS, provider or financial-semantic change; no ledger value, calculation or capture behaviour altered.
- Affected capability or project boundary: desktop primary navigation, the capture chooser, and the Inbox page's action row.
- Status impact: candidate until merged. On merge desktop stops offering two capture primaries at once, and the two acquisition paths gain a home instead of depending on a duplicate button.
- Lifecycle impact: authority transition. No slice is completed or promoted — none is registered. It carries the board's move to PR #504's merged commit `cfba0b18`, the transition this PR is the same-PR projection for.
- The decision this unblocks: PR #480 attempted the same removal, and I got it wrong — the sidebar chooser was then the only shell route to `/capture/paste` and `/capture/upload`. The unanswered question was never whether to remove the duplicate, it was where the other two paths live afterwards.
- Research, primary sources only: YNAB documents File-Based Import as an action inside the account register; Actual Budget's own docs place `Import` beside `Add New` inside an account; Monarch places CSV upload under Accounts. **None of the three offers a global "how do you want to capture?" chooser** — bulk import always sits in the context it changes. Applied to MoneyFlow, paste and upload never write to the ledger; they produce Inbox candidates, so their context is `/inbox`. The Inbox was previously the screen candidates land on with no way to acquire any.
- Changed: `src/lib/nav-ia.ts` gains `DESKTOP_SIDEBAR_NAV` carrying the reasoning; `app-shell.tsx` renders it and loses the capture action branch, the `captureOpen` state, `openCapture`, the `CaptureSheet` component and the `CAPTURE_OPTIONS` import; `app-shell.module.css` loses 6 dead rule blocks and 9 dead selectors from shared lists; `inbox-page.tsx` gains the two acquisition actions; two contract tests updated.
- An unforeseen consequence, found by reading rather than assumed: with the sidebar trigger gone, `openCapture` had no caller — mobile's centred `Ghi` navigates to `/capture/quick` and never opened the sheet. `CaptureSheet` was therefore dead code duplicating the `/capture` page, which has a URL, a back button and is shareable. It was deleted rather than left dangling, which is exactly the exported-and-tested-but-unreachable trap.
- Verified by crawling the built app from `/dashboard` at 1366px using only visible links: `/capture/paste` and `/capture/upload` moved from **3 steps to 2**, and none of the other 21 routes regressed. Desktop shell buttons went from `Nhập nhanh | Ghi chi tiêu` to `Ghi chi tiêu`; the phone shell is unchanged at `Ghi chi tiêu | Thêm7`.
- Verified: `typecheck`, `lint`, `check:architecture`, `check:css-ownership`, `check:code-css-ownership`, `test:ci-policy`, `check:knowledge` exit 0; `npm test` **1226 pass, 0 fail**; `npm run build` exit 0; the desktop, Android and keyboard audit projects **136 passed**.
- Two tests changed, and the distinction from PR #480 matters. There I edited an audit test to fit my change before understanding it. Here `modal-dialog.responsive.audit.spec.ts` lost its subject — the chooser is a page, not a dialog — so rather than delete the guarantee it was replaced with a stronger one: desktop keeps exactly one capture primary and every capture path stays reachable, which catches both a returning duplicate and a stranded path. `app-shell-phase3-contract.test.ts` drops the assertion about the deleted sheet and **adds** one that it must not return.
- On the Inbox being unfinished, raised by the owner mid-work and checked rather than assumed: it is not. 11 RPCs exist, 10 pgTAP files exercise `approve_inbox_candidate` across roughly 173 assertions and 3,200 lines, and driving a browser through the flow works end to end — paste, analyse, "Tìm thấy 1 giao dịch", then a full review dialog with type, date, place, amount, category and account plus `Lưu thành quy tắc` / `Từ chối ứng viên` / `Đánh dấu có thể trùng` / `Duyệt vào sổ`, with no JavaScript errors. What was true is that it was nearly invisible: measured before this change, the desktop shell exposed only `/dashboard`, `/transactions`, `/accounts` and `/settings`, the unread badge lives on a mobile-only control, and the sole route in was one dashboard link. A capability nobody can find reads as unbuilt.
- CI caught one thing the local run could not, and the fix keeps the guarantee rather than dropping it: `critical-browser.audit.spec.ts` opened the deleted `Ghi giao dịch` sheet from the deleted `Nhập nhanh` button on every viewport above 760px. Its actual guarantee is that a shell modal closes on Escape and hands focus back to the control that opened it — `modal-dialog.responsive.audit.spec.ts` checks focus trapping and Escape but never the hand-back, so the desktop branch was re-pointed at the transaction dialog, which still exists, instead of being skipped. All nine chromium audit projects then passed: **481 passed**.
- Remaining: the second half of the issue's Slice 1 — removing `DashboardPlanningColumn` — is not in this PR. Its premise was checked and holds: `DashboardHeaderSections` does exist and does render `PLANNING_LINKS`, so removing the column would not strand `/budgets`, `/goals` or `/income-templates`. It is a separate product judgement and the issue itself requires one bounded slice at a time. No performance claim is made here; script bytes were not re-measured because this change removes markup, not client behaviour. `/timeline` remains unreachable from `/dashboard` by visible links — a pre-existing defect this PR neither caused nor fixed.
- Environment limitation, recorded rather than worked around: WebKit cannot run on this machine — all 23 tests in the `webkit-tablet` project fail identically at `page.goto` with `WebKit encountered an internal error`, before any assertion. The Safari half of the cross-device audit is therefore proven by CI only, not locally.
- Production/provider evidence: not applicable. All measurement was against a local production build in demo mode.
- Snapshot update: `docs/research/CURRENT_PROJECT_MEMORY.md` and the board move to PR #504's baseline `cfba0b18` and carry the PR #505 projection. No capability row changes.
- Superseded issue, roadmap or claim: supersedes PR #480's conclusion that the sidebar chooser was the only possible desktop entry to paste and upload — it was the only *shell* entry, and re-homing them on the Inbox is both shorter and better placed. Partially advances #426 Slice 1.
