# PR #681 — Deterministic rules fire on the capture payee field

- Date: 2026-09-23
- Change class: Class 2 (bounded capture-dialog flow + one domain helper; no migration, schema or RPC change)
- Affected capability or project boundary: `src/lib/inbox/apply-rules.ts` (new pure `resolveRuleCategoryFill`), `src/components/add-transaction-dialog.tsx` (shared `applyRuleFill` on both text fields, learned chip gated by `!autoRuleHint`), tests in `src/lib/inbox/apply-rules.test.ts` and `src/lib/ghi-chi-dialog-contract.test.ts`.
- Status impact: rules saved from Inbox review via "Lưu thành quy tắc" (`field:"merchant"`, built by `buildConfirmedReviewRuleSeed`) now fire inside the manual-add dialog — previously they never could, because `applyPayeeChange` did not consult rules and `applyNoteChange` passed an empty merchant haystack.
- Changed: `resolveRuleCategoryFill(rules, {kind, merchant, note}, categories)` returns `{match, categoryId, hint} | null`: the typed payee is the merchant haystack, the note draft the note haystack, and the draft kind is enforced so a wrong-`categoryKind` rule can no longer shadow a same-kind lower-priority match. Both `applyPayeeChange` and `applyNoteChange` delegate to one `applyRuleFill` that fills only the draft category and surfaces the existing `tự động theo quy tắc “X” → Y` attribution hint; a rule's merchant normalization is deliberately absent from the result so typed payee text is never rewritten, and `categoryTouchedRef` still protects an explicit category choice. A visible rule fill suppresses the learned `Gợi ý` chip instead of competing with it; no match leaves chip behavior unchanged.
- Verified: typecheck clean, lint 0 errors (1 pre-existing warning in quick-add-defaults.test.ts), `npm test` 1657/1657 (new: 6 capture-fill unit tests + 1 dialog-contract test), check:knowledge, test:ci-policy 191/191, check:architecture, check:css-ownership. Browser smoke and visual audit delegated to CI lanes.
- Remaining: the fill re-evaluates only on payee/note edits — switching kind resets the draft default as before rather than re-running rules; rules still reach the dialog via `readStoredRules` (localStorage), so authenticated-mode rule availability is unchanged from before.
- Production/provider evidence: none (draft-only UI fill; production verification remains an owner decision post-merge).
- Superseded issue, roadmap or claim: none.
- Lifecycle impact: if capture later needs payee normalization-as-offer or rule evaluation on kind switch, extend `resolveRuleCategoryFill`/`applyRuleFill` rather than adding a second rules path.
