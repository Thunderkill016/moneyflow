# PR #676 — Running-balance column in the single-account register

- Date: 2026-09-22
- Change class: Class 2 (bounded UI/flow — one new domain module plus one column in the existing ledger list)
- Affected capability or project boundary: `src/lib/running-balance.ts` (new pure module: `resolveRegisterBalanceScope` + `buildRunningBalance`), `src/lib/transactions/contracts.ts` (`AccountOption.balance?`, integer minor units), `src/server/finance.ts` (attaches already-fetched `account_balances` rows to workspace accounts), `src/lib/demo/transaction-fixtures.ts` (demo snapshot balances mirroring `demoAccountRows`), `src/components/transactions/transactions-workspace.tsx` + its CSS Module (conditional "Số dư sau giao dịch" column, 5-track desktop grid, 4-track mobile reflow).
- Status impact: closes the register-cum-balance gap vs Actual/YNAB-style comparators; the per-account ledger view now shows cumulative position per row instead of bare amounts.
- Changed: when the account filter resolves to exactly one account, every row carries the balance right after that transaction — anchored at the account's current balance, reconciled against the mount-time ledger via `reconcileAccountBalanceSnapshot` so session mutations and optimistic rows shift the column consistently. Balances are computed over the full register in display order (newest first), so search/kind/date filters hide rows without changing numbers. Transfer legs move the scoped account both directions; a leg whose counterparty resolves to a different currency voids only the rows below it (rendered "—") — never a mixed-currency total. "all"/unknown/duplicate-name/missing-balance scopes hide the column.
- Verified: running-balance.test 10/10 (scope, ordering, both transfer directions, register isolation, session-delta reconciliation, filtered-row stability, FX poisoning, fail-closed overflow, empty register); full suite 1534/1534; typecheck; lint (1 pre-existing warning); build 51 routes; check:knowledge; ci-policy 191/191; check:architecture; check:css-ownership; check:dead-css. Demo smoke: `/transactions?account=MB Bank` renders 15.454.000 / 15.517.000 / 15.803.000 ₫ top-down; unscoped view shows no column.
- Remaining: the column reflects the ledger as loaded — balances on another device or after external writes appear on reload, same convention as `totalBalance`. Rows name-matched by the filter but outside the resolved account id degrade to "—". No per-account balance polling exists by design.
- Production/provider evidence: none (read-only presentation; browser smoke delegated to CI lanes).
- Superseded issue, roadmap or claim: none.
- Lifecycle impact: if per-account balances later feed budgeting or safe-to-spend, the `AccountOption.balance` contract and the reconcile-on-mount pattern are the seam to reuse; if users ask for a balance column in multi-account views, the honest answer is per-account totals, not one mixed sum.
