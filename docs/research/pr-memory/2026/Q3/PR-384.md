## Self-review and provider findings

### P1 — inline Git alias escape — RESOLVED

The first transplanted #380 guard allowed an inline Git alias escape such as `git -c alias.ship='!git push origin HEAD:main' ship`.

Remediation:
- dangerous/unknown Git global options fail closed;
- branch-control and history-integration operations are not available to the child;
- Git commands use an explicit operation allowlist;
- commit amend and hook bypass are rejected.

### P1 — dispatcher safety tests absent from provider CI — RESOLVED

`npm test` covers `src/lib` and the old `test:ci-policy` omitted dispatcher tests. The dispatcher + command-guard suites are now part of `test:ci-policy`, so protected policy verification must execute them.

### P1 — GitHub write surface remained broader than delivery authority — RESOLVED

An intermediate guard still admitted write-capable subcommands such as issue/PR mutation, run cancellation/rerun and arbitrary `gh api` paths because it allowed broad top-level command families.

Remediation:
- exact GitHub CLI subcommand allowlist: auth status, issue reads, PR reads/checks, repo view, run reads/watch, and PR create only;
- all `gh api`, alias, secret, issue-edit/close, PR merge/edit/ready/review/close and run cancel/rerun/delete paths fail closed;
- `gh auth status --show-token` and `-t` fail closed because the official GitHub CLI exposes the token on those paths.

### P1 — push / PR delivery was not bound tightly enough — RESOLVED

An intermediate guard allowed a wider push/refspec surface and draft PR creation did not require the current isolated branch explicitly.

Remediation:
- Git push is limited to `origin HEAD` with only optional upstream flag and is allowed only from an unambiguous non-main branch;
- force/deletion/arbitrary refspec pushes fail closed;
- fetch destination refspecs and remote mutation fail closed;
- `gh pr create` runtime policy requires draft mode, explicit same-repository non-main `--head`, base `main` when specified, and the head must match the current isolated branch;
- `--dry-run`/`--web` PR creation paths are blocked because the dispatcher requires the explicit non-interactive delivery path.

### P1 — original PATH exposed an easy guard bypass — RESOLVED WITH NAMED RESIDUAL

The first guard passed the original PATH to the child and then restored it before spawning real `git`/`gh`, making the wrapper easy to bypass and allowing nested `gh` Git calls to escape the Git guard.

Remediation:
- real Git/GitHub executables are resolved by the trusted parent before launch and embedded in the private guard launchers;
- the child no longer receives an `MONEYFLOW_DISPATCHER_ORIGINAL_PATH` escape variable;
- guard-first PATH remains in place when a real tool is spawned, so Git invoked internally by `gh` continues through the Git guard.

### P1 — protected merge exposed a CodeQL command-injection alert — RESOLVED IN CODE, RECHECK PENDING

A squash merge attempt on exact head `1a5c7ad1a7db0175b0a5c06d5c43356a98fcc7f4` was rejected with HTTP 409 by the active ruleset even though the CodeQL workflow itself concluded success. The CodeQL check output reported **1 new medium-severity alert**. Its annotation was:

- query: `js/shell-command-injection-from-environment` (`Shell command built from environment values`);
- file: `scripts/agent-dispatcher/dispatcher.mjs`;
- sink: generic `spawnSync(command, args, ...)` in `defaultRun`.

This is treated as a real security finding, not a provider false positive. Official CodeQL guidance recommends hard-coded executable literals with dynamic values passed as arguments.

Remediation:
- `defaultRun` now dispatches only fixed literal executables: `git`, `gh`, `codex` and `node`;
- unsupported executables fail closed before process spawn;
- transport tests no longer invoke `/usr/bin/env` or `/bin/bash`; they use literal `node` probes for environment propagation and large-output coverage;
- a regression asserts that an unsupported executable such as `bash` is rejected.

The next valid security evidence must come from CodeQL on the new exact head, and the protected merge gate must observe zero blocking alerts before merge.

## Evidence boundary

The process-level command guard is defense in depth. It constrains ordinary inherited `git`/`gh` execution paths but is **not** an OS sandbox or hostile-process boundary. A deliberately hostile child can still attempt an absolute executable path or spawn lower-level processes outside the PATH wrapper. Codex sandboxing is the primary execution boundary; repository protection, exact-head CI and owner-scoped credentials remain independent safeguards.
