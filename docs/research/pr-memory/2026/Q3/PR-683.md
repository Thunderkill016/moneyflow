# PR #683 — Explicit noticeTone at call sites over keyword-sniffed toast tone

- Date: 2026-09-23
- Change class: Class 1 (bounded code in one subsystem — shell notice presentation — straightforward rollback)
- Affected capability or project boundary: `src/lib/toast-presentation.ts` (new pure resolver: `resolveToastPresentation(notice, { hasAction, tone })` + `ToastPresentation`/`ToastPresentationOptions` types), `src/lib/toast-presentation.test.ts` (new, +4 tests), `src/components/layout/app-shell.tsx` (local `resolveToastPresentation` removed; `noticeTone` prop now feeds the resolver instead of being a dead prop), `src/components/transactions/transactions-workspace.tsx` (`showNotice` requires a `tone` second param; `showDeleteNotice` declares `neutral` when an undo offer is real, `warning` when every selected row was skipped), `src/components/inbox/inbox-page.tsx` (`showNotice` as a stable `useCallback`; ~20 call sites declare tones), `src/components/moneyflow-dashboard.tsx` and `src/components/inbox/capture-quick-page.tsx` (`showNotice` helper; confirmations declare `success`).
- Status impact: toast tone is now caller-declared on the four notice surfaces the task named; the Vietnamese keyword heuristic ("lỗi"/"thất bại"/"không thể" → error, "cảnh báo"/"chưa"/"yêu cầu" → warning, "thông tin"/"chi tiết"/"đang"/"khôi phục" → info, default success) survives verbatim as the fallback for callers that never declare a tone. Real mistone fixed: "Đã chọn N ứng viên Sẵn sàng. Chưa có giao dịch nào được ghi sổ." rendered warning before, renders success now. Deliberate tone shifts per spec: undo offers render `neutral` (was `info`), save confirmations carrying the "Sửa" action render `success` (was `info`).
- Changed: precedence is explicit tone > attached action (icon pinned to `restore`, tone default `info`) > keyword heuristic > `success` default. All save/RPC failure notices declare `error`; validation/empty-target notices `warning`; managed-elsewhere and keyboard hints `info`; confirmations `success`. Notice + tone state move as a pair in every page (helpers always set both; every clear resets tone) so a stale tone cannot leak into the next notice. No user-facing copy changed.
- Verified: typecheck clean; lint 0 errors (1 pre-existing warning, `quick-add-defaults.test.ts:347` — same as #680); `npm test` 1654/1654; check:knowledge; test:ci-policy 191/191; check:architecture. Worktree `wt-notice-tone` used a hardlinked `node_modules` copy (Turbopack/symlink convention from #680); `.env.local` copied for parity — not needed by the gates.
- Remaining: ~24 other `AppShell` notice surfaces (goals, budgets, imports, settings, etc.) still rely on the heuristic fallback — intentional scope bound; they can adopt `noticeTone` incrementally until the heuristic can be retired. Browser-rendered tone colors verified through the resolver unit tests and CI lanes, not a physical device.
- Production/provider evidence: none (presentation-only; no migration, no provider writes).
- Superseded issue, roadmap or claim: none.
- Lifecycle impact: if a notice surface ever needs a tone the `ToastTone` union lacks ("neutral" | "info" | "success" | "warning" | "error"), extend the union in `src/components/ui/toast.tsx` first; if every caller declares a tone, the keyword fallback in `toast-presentation.ts` becomes deletable — the tests pin it as fallback until then.
