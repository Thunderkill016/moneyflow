## Why the deployment path was broken

`supabase db push` refused to run: 12 remote versions had no local file. The CLI's
suggested `migration repair --status reverted` would have falsified another
product's record of its own database. Forced, the push would have applied seven
unrelated MoneyFlow migrations, one of which has six non-idempotent statements
and would have failed partway through.

## Findings worth keeping

- The migration history table stores SQL **comment-stripped** with a trailing
  `;;`, so `migration fetch` output is a lossy normalization and must not replace
  reviewed files.
- Five migrations were the same migration retimestamped — byte-identical after
  normalization, resolved as pure renames to production's canonical versions.
- `20260715001400` and `20260715001500` are superseded by the applied
  `20260725035128`, which redefines the same three objects. Pushing them would
  downgrade two live functions.
