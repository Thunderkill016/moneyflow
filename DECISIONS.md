- 2026-10-16 — D4 "similar transactions" detail block waived: mobile has no transaction-detail surface (row tap opens the editor/select-mode, no detail sheet exists to host it), and the Copilot 3.4 intent — same-payee month total + similar list — is already served by the payee ranking's "N giao dịch"/total rows plus the `TransactionQuery.payee` drill-in, which opens exactly that payee's timeline. Building a new detail screen for one block exceeds the slice's "pure presentation" scope.
- 2026-10-16 — D4 "pending" timeline chip waived: `Transaction`/`TransactionQuery` carry no pending/posted field — every ledger row is a posted fact; pending exists only upstream in the inbox capture-candidate surface, which already gates itself on review status. A chip filtering on a nonexistent column would fabricate a distinction the data doesn't have. The payee chip shipped instead as an exact-match "Người nhận" field on the existing query plumbing.
- 2026-10-16 — D5 ships no swipe-to-approve and no bulk inbox approve: approval posts a ledger row, and MoneyFlow law says candidates are not ledger rows until explicit per-item approval inside the review sheet where account/category and the plan verdict (duplicate/transfer) are visible. A gesture or one-tap bulk action can't carry that context without turning approval into a blind write; the shipped gestures only accelerate non-posting actions (mark-reviewed on posted rows, confirmed reject in the queue). Reject swipes still pass the same confirm dialog + RPC as the button — the gesture saves the tap, never the confirmation.
- 2026-10-16 — Activity swipe is one-directional (right = "Đã xem" only, no left swipe): the row already carries the visible delete icon + long-press delete, and a second horizontal affordance would put a destructive and a routine gesture one thumb-slip apart. Flagging a clean row back to needs_review stays in select-mode bulk where it's deliberate, not a flick.
- 2026-10-16 — `loadNeedsReviewTransactions` reads the flagged id list unbounded (count = full backlog) while only `previewLimit` feed rows are fetched: a capped count would understate the queue the card exists to warn about; the two-hop shape (transaction_review_feed ids → transaction_feed fields) mirrors `_withReviewStatus` in the other direction because review_status lives off the feed view.
- 2026-10-17 — D11 "include in monthly plan" toggle waived: no `include_in_monthly_plan` field (or equivalent) exists in the schema, the Data API, or the web goal contract, and inventing a device-local flag that pretends to feed the D3 remainder math would fabricate planning semantics. The honest shipped analogue is the goal tile's reserve line ("Đã dành X — còn có thể dành Y"), which surfaces the same earmarking pressure without claiming money the plan read doesn't subtract.
- 2026-10-17 — D10 watchlist pins persist device-local (SharedPreferences `mf_watch_items`), not server-side: there is no watchlist table/RPC, and a pin is a private "keep an eye on it" bookmark, not financial truth — losing it on reinstall loses nothing monetary. The pin affordance only renders when BOTH seams are wired so a dead "Ghim" can't ship in a test harness.
- 2026-10-17 — D9 month-close digest is a one-shot per month (not a repeating alarm): `zonedSchedule` repeat modes can't express "last day of month" (day-31 semantics differ per month), so `refreshMonthCloseDigest` re-arms on every sign-in/refresh path; missed-window states re-resolve on the next app wake rather than firing a stale digest.

- 2026-10-16 — D12 reuses `monthly_budgets` (+`period_kind`, `month_start` as the per-kind anchor) instead of a parallel weekly table: one RPC/view/write path serves both cadences, and the conflict target (user, category, period_kind, anchor) keeps a weekly and a monthly limit coexisting honestly — including a first-of-month Monday. Admitted period kinds are exactly {monthly, weekly}; quarterly/yearly would be unwriteable dead contract today and are a small follow-up when needed.
- 2026-10-16 — Weekly budgets anchor on Monday (VN civil week start), never the viewed day: the anchor is a stored fact the check constraint enforces (`extract(isodow)=1`), so a mid-week save can never store a drifting "7 days from today" window that disagrees with itself next open.
- 2026-10-16 — D13 exclusion flag rides `update_money_transaction` (`p_excluded_from_reports`, null = preserve) instead of a standalone set-flag RPC: `transactions_set_updated_at` bumps `updated_at` on every UPDATE, so a chained flag write could never reuse the form's optimistic-concurrency token — it would have to return the rotated token and re-feed it, adding a second round-trip for zero integrity gain. One write seam keeps flag+fields atomic behind one token. The reconciled-row guard exempts the flag (metadata like payee/goal_id: reconciliation proved the money moved, not that it belongs in a report); transfers stay unreachable via the existing kind lock since a flag on a transfer would be dead UI.
- 2026-10-16 — D13 scope is reports only: flagged rows still count toward account balances, budget progress, safe-to-spend and the dashboard — the money really moved, and the flag is report scoping, not ledger hiding (Money Manager/Monarch semantics). The activity list keeps the rows and marks them "Đã loại khỏi báo cáo" so drill-in arithmetic stays explainable. Known divergence: the web /reports aggregation does not read the flag yet — the column ships with the mobile contract documented here; web parity is a follow-up item, not implied by this slice.
